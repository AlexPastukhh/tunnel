# Работа с этим репозиторием

Начать с [навигации по задачам](docs/README.md) и [архитектуры](docs/ARCHITECTURE.md); для журналирования и запретов — [AUDIT](docs/AUDIT.md). Эти страницы не заменяют live-проверку.

Сначала читать README.md и docs/CURRENT_STATE.md. Исторические документы не использовать как текущую конфигурацию.

- Выполнять задачу пользователя. Не трактовать подключение MCP-плагина как запрос создать сайт.
- Различать native HOST, native Repo Docker и два Site MCP endpoint. Диагностика одного не доказывает состояние другого.
- HOST: только разрешённые файловые/терминальные действия. Автоматизация основного Windows GUI, screenshots и ввод не разрешены.
- Repo Docker: /workspace/repos и /workspace/files напрямую изменяют Windows-файлы. /workspace/repo — отдельный внутренний volume.
- Не публиковать ключи, профили с секретами, логи с payload, snapshots ZIP или приватные upstream URL. Не расширять аудиторию Site или экспорт Bridge попутно.
- После timeout мутации сначала проверить состояние. Не повторять вслепую.
- Не удалять/чинить metadata Windows linked worktrees из Linux только из-за недоступных Windows-путей.
- При изменении runtime, инструкций или tool presentation обновить docs/INSTRUCTIONS.md и соответствующие текущие документы. Записать, что реально перезапущено/опубликовано и проверено.
- Для Observatory читать [текущий README V1](observatory/v1/README.md). После изменения поддерживать там source/версию, установленное состояние, проверки и открытые вопросы отдельно; в общих docs оставлять ссылки. Исторические candidate-статусы не считать реестром текущей установки.
- runtime/ — исходники-копии. Для применения нужен явный перенос в действующую установку и проверка. Site исходники принадлежат отдельному Sites Git, не этому репозиторию.

## Общий workflow агентов и документация

- Для задач общей разработки через Repo/G2, ручной проверки приложений/игр, медиа, CI и локальных ИИ читать [точку входа](docs/agent-workflow/README.md), затем REQUIREMENTS, STATE и последние записи JOURNAL.
- После значимого решения или проверки обновлять текущий план и журнал; различать сообщение пользователя, наблюдение инструмента, вывод и предложение. Не выдавать файловый smoke за запуск приложения или полный security PASS.
- Пользователь поручил вести осмысленные локальные Git-коммиты планов/документов этой инициативы. Проверять diff и включать только относящиеся к задаче файлы. Push и применение runtime остаются отдельными действиями.
- Изменения Windows-хоста и пользовательских профилей готовить как конкретные команды для ручного исполнения пользователем. Проверки и проектные действия внутри уже разрешённой среды выполнять в её пределах.
