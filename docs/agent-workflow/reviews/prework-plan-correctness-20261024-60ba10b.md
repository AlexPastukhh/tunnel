**Предмет:** `docs/agent-workflow/STATE.md`, раздел «Ближайший план», N-01–N-08, в локальном коммите `60ba10be6892a8c9874d8f3f492be629bfe6ae05` репозитория `AlexPastukhh/tunnel`. ## 1. Target, версия и границы

Проверяемая единица работы — **review корректности общего плана**, включая его соответствие пользовательской цели, полноту сценариев, порядок действий, условия готовности, безопасность и удобство использования. Фокус не ограничен ближайшим запуском Godot.

Родительский контекст — общий workflow разработки через Fortis Repo, ограниченный Windows-исполнитель G2, MCP, CI, локальные ИИ и Observatory. Формальное принятое дерево SRU для этого workflow в прочитанных четырёх основных документах не установлено. Для подготовки review новое дерево реализации не требуется.

Идентификаторы `N-01`–`N-08` в STATE обозначают **пункты ближайшего плана**, а не User Needs. Ниже они записаны как `STATE.N-01`–`STATE.N-08`. Новые ID действуют только внутри этого документа и не переименовывают исходные записи.

В scope будущей проверки входят:

- весь маршрут от задачи агенту до ручного использования результата и следующей итерации;
- все семь заявленных сценариев S-01–S-07; различия между общим направлением и готовностью конкретной версии;
- применимые ранее принятые границы G2/Repo, источники утверждений и пределы уже выполненных проверок;
- обоснованность следующих шагов, зависимостей и предлагаемых способов реализации.

В scope не входят реализация шагов STATE, запуск игры, установка компонентов, изменение ACL/mounts/runtime, новая CI-приёмка, полный аудит компьютера и исправление рабочего плана. Для корректности самого плана возможны чтение источников, разбор конкретных ситуаций и адресная сверка существенного технического утверждения. Это не обещание заново испытать все среды.

**Явное допущение A-01:** слово «план» относится к текущему общему плану в STATE, а не ко всем 58 критериям прежнего G2-плана. Основание — последовательность текущей работы и указатели README/CURRENT_STATE. Развилка отражена в F-U-01; принятие C-01 с этим target её закрывает для данной работы.

S-01–S-07 — явно названный пользователем охват общего workflow. Требование одинаковой реализации всех сценариев из этого не следует. Конкретные способы безопасного исполнения и приёмки должны служить N-WF-01/02 и FR, а не заменять их.

Снижение повторного ввода пароля и работа из основного профиля — **предпочтения**. Переключение в G2 допустимо. Оценка «за минуту» сообщена пользователем; это не измеренный SLA. Passwordless/autologon не установлен как обязательная реализация.

### Уже выполненные решения и кандидатные положения

- Рабочая документация уже находится в `tunnel/docs/agent-workflow`; локальный Git-checkpoint существует. Это установленное место ведения работы, а не основание считать все формулировки документов отдельно принятыми пользователем.
- Узкий ACL grant к одному проекту вручную выполнен пользователем. Файловый тест G2↔Repo записан как ограниченный результат. Его успешность не означает принятие или готовность всех дальнейших способов реализации.
- Перенос Docker под G2, выдача G2 Docker API, новая VM, обязательное дублирование всех репозиториев и конкретный способ показа окна из основного профиля не установлены как принятые решения.
- Вопрос пользователя «сделать доступное в основном профиле в Docker доступным в G2» — исходная гипотеза о способе работы. Не превращать её в требование идентичной установки Docker в двух профилях.
- Идея Git и осмысленных коммитов в `tunnel` реализована как способ документирования. Нынешнее правило атомарного принятия нельзя задним числом использовать для объявления прошлой фиксации ошибочной.
- Часть I-01–I-14 подробнее прямых реплик пользователя: например, конкретный порядок восстановления, фиксация версии при приёмке и устройство отзыва полномочий. Для каждого существенного вывода будущий review должен установить происхождение: ранее принятое ограничение, технический вывод, candidate/inferred условие или рекомендация. Заголовок «инварианты» сам этого не доказывает.
- Применимые ранее принятые G2/Repo-ограничения искать по ссылкам действующей документации. Старые NEXT/BLOCKED и проектируемые механизмы не объявлять текущими обязательствами без проверки версии и статуса.

Новых FR проекта и новых committed implementation decisions этот pre-work не вводит.

## 4. DRLD и связь с реализацией

В прочитанных основных документах есть описание цели, сценарии и критерии, но не установлена отдельно принятая подробная версия каждого реального пути. Таблица ниже — **candidate/inferred реконструкция для направления review**. Она не является принятой DRLD и не требует нового канонического файла.

Во всех строках польза, концепция и подробный путь относятся к одному сценарию. Известные пользовательские условия сохраняют самостоятельную силу; предложенные переходы, роли и обработка исключений требуют проверки.

| Сценарий | Fundamental Benefit → Scenario Concept → Detailed Desired Real-Life Scenario |
| --- | --- |
| S-01 Приложение | **Польза:** пользователь получает работающее приложение и может оценивать изменения. **Концепция:** агент разрабатывает в выделенной среде, пользователь вручную проверяет результат. **Путь:** пользователь задаёт проект/платформу и нужные функции → агент получает необходимые входы и зависимости, меняет файлы, собирает/тестирует → результат определённой версии доступен выбранному исполнителю → пользователь запускает и проверяет → передаёт обратную связь для следующей итерации. Польза возникает при доступном проверяемом результате и повторяется по итерациям. Нехватка входов/компонентов требует конкретного запроса; изменение хоста идёт через FR-WF-03 |
| S-02 Игра | **Польза:** можно реально поиграть и проверить, что получилось. **Концепция:** работа агента с проектом связана с полноценной ручной игровой проверкой. **Путь:** выбранный проект и его версия → изменение кода/сцен/ресурсов и проверки агента → доступный импорт/сборка и подходящий игровой исполнитель → пользователь проверяет управление, изображение, звук и иные нужные функции → замечания возвращаются агенту. Польза возникает при игре, а не только при чтении файлов или PNG. Если маршрут лишает нужного ввода/GPU/звука, его пригодность пересматривается |
| S-03 Изображения/3D | **Польза:** пользователь видит и использует визуальный результат. **Концепция:** агент создаёт материал через выбранные инструменты и передаёт удобный для просмотра/работы результат. **Путь:** задание/референсы → генерация или редактирование → доступный экспорт и, когда нужен, рабочий проект → пользователь осматривает/сравнивает → задаёт изменения. Польза возникает при просмотре и использовании результата. Открытие проекта с плагинами/скриптами отдельно сопоставляется с правами исполнителя |
| S-04 Аудио | **Польза:** пользователь слышит результат и может его оценивать. **Концепция:** агент создаёт/обрабатывает звук, пользователь прослушивает и уточняет. **Путь:** входы и задача → обработка/генерация → доступная версия аудио, при необходимости рабочий проект → воспроизведение/перемотка/сравнение пользователем → следующая итерация. Польза возникает при прослушивании и дальнейшем использовании. Недоступный формат, плагин или устройство не маскируется успешной записью файла |
| S-05 Настройка хоста | **Польза:** пользователь получает нужную настройку, сохраняя контроль над изменением компьютера. **Концепция:** агент подготавливает, пользователь исполняет. **Путь:** установлена необходимость и текущие условия → агент даёт точные команды, последствия, проверку и уместный откат → пользователь вручную выполняет → результат проверяется → при сбое применяется подходящее восстановление. Агент не использует другой канал для самостоятельного применения настройки |
| S-06 CI | **Польза:** агент получает независимый результат сборки/проверки и может исправлять работу; пользователь получает привязанный к версии артефакт. **Концепция:** согласованный CI-маршрут дополняет локальные проверки. **Путь:** выбранная версия и разрешённое действие запуска → run с известными правами/данными/лимитами → настоящие логи и артефакты, связанные с commit/run → анализ и исправление → при необходимости следующий разрешённый запуск. Польза может возникать после каждого run. Ошибка, задержка или исчерпание лимита фиксируется явно; право push/запуска не выводится из наличия плагина |
| S-07 Observatory | **Польза:** пользователь видит результаты/состояние работы агента без ручного чтения каждого файла. **Концепция:** агент пишет доступные ему данные, доверенный потребитель отображает их, управление имеет отдельные полномочия. **Путь:** согласованы место и формат → агент пишет данные → потребитель принимает/обрабатывает их → пользователь видит результат → управляющее действие, если нужно, проходит свою авторизацию. Польза возникает при достоверном отображении. Поведение при неполном/неподходящем входе и восстановление — предмет проверки, а не уже подтверждённая гарантия |

**Scenario Realization Composition:** STATE.N-01–N-08 — существующая дорожная карта, а не автоматически полное принятое SRU-дерево. Будущий review проверит покрытие переходов: доступ к входам → работа агента → подходящий исполнитель → ручное использование → обратная связь; отдельно CI и потребление данных. Если обнаружится пробел, сначала сформулировать finding/Proposal, а не молча создавать новые SRU или менять Scenario.

## 5. Практические условия и ценность этой работы

**Почему сейчас:** после файлового доступа следующим шагом мог бы стать импорт/запуск Godot. Проверка общего плана до дальнейшей настройки может выявить неверный порядок, пропущенный пользовательский путь или лишнее расширение доступа. Без неё работа продолжится по ещё не проверенной дорожной карте.

**Достаточный объём:** source-based review всего STATE и применимых оснований, с адресной проверкой существенных неоднозначных утверждений. Полная повторная приёмка всех сред дала бы другой результат и потребовала бы запусков, ресурсов и участия пользователя; она не включена в эту единицу.

| Поверхность затрат | Известное и влияние на выбор |
| --- | --- |
| Прохождение будущего workflow | Переключение профиля допустимо, но нежелательно; пользователь сообщил ориентир около минуты. Частота проверок, активное время, ожидание запуска, задержка показа и парольные действия не измерены. Проверять повторный ручной труд качественно; не объявлять выбранный просмотр быстрым без evidence |
| Реализация workflow | STATE документирует ограниченные CPU/RAM контейнера и неподтверждённые графические/медийные возможности. Это основания оценивать конкретный проект и зависимости, а не объявлять среду универсально готовой или невозможной |
| Жизненный цикл | Имеют значение поддержка копий, повторная настройка, восстановление, отзыв доступа и стоимость будущих изменений. Не добавлять VM, launcher, новый gate или реестр только ради возможного будущего спроса |
| Нынешняя работа помощника | Использовать уже доступные документы и записанные доказательства; запросы к MCP/GitHub и участие пользователя имеют стоимость. Не повторять файловый smoke, общий сбор характеристик, CI и многоступенчатые экспорты без конкретной причины |

Hard deadline, бюджет и выделенные ресурсы на review не заданы. Effort, календарная длительность и critical path количественно не оценены; обещаний по часам/датам нет.

**Cost / Timing Delta:** выбранное review шире проверки только STATE.N-02/N-03 и покрывает исходный запрос обо всём workflow. Оно уже полной live-приёмки семи сценариев и не требует её настроек/запусков. Денежная и временная delta неизвестна; сравнение качественное. Проверка только Godot оставила бы существенный общий scope вне результата. Полная live-приёмка не нужна для каждого вывода о структуре плана; если без конкретного опыта вывод не устанавливается, это будет адресный gate или ограничение review.

### F-U-01 — какой именно план должен получить полный вердикт

**Type:** Decision Uncertainty. **Level:** CURRENT относительно постановки этой проверки. **Semantic target:** граница review `agent-workflow/STATE` ↔ подробный прежний G2-план.

Известно: последняя работа создала общую дорожную карту STATE; в том же репозитории есть отдельный подробный план защиты G2. Не установлено явным путём в последней реплике, какой из них пользователь назвал «планом».

- **Вариант A / PR-R-01:** весь STATE.N-01–N-08 с применимыми источниками. Даёт проверку общего workflow, включая ручной путь и семь сценариев.
- **Вариант B / PR-R-03:** прежний подробный G2-план как самостоятельный полный target. Меняет охват и перечень критериев; сам по себе не даёт вердикт обо всём общем workflow.

Это разные предметы проверки. Их объём и длительность количественно не оценены; скрыто заменить один другим нельзя. По контексту рекомендован A.

| Атрибут | Значение и основание |
| --- | --- |
| Disposition | `unresolved` на момент pre-work |
| User Review Priority | `HIGH`: выбор меняет основной scope и полезность итогового вердикта |
| Intervention Priority | `NEXT`: требуется перед исполнением review; нет данных о hard deadline или необратимой потере от ожидания |

Причина ограниченной Autonomy: основной target хорошо следует из контекста, но явный другой пользовательский target имел бы приоритет. Рекомендация не заменяет его решение.

## 12. Candidate Execution Plan

1. **Закрепить target и ограничения после принятия C-01.** Использовать выбранный commit. Это предотвращает review другого плана; повторный сбор всей среды не нужен. Если текущие файлы изменились, отделить точную исходную версию от новых изменений, не смешивать выводы.
2. **Восстановить применимые основания.** Сопоставить пользовательские реплики, S/I, WF-записи и ссылки на прежние принятые решения G2/Repo. Читать дополнительно только материал, влияющий на вывод. Не объявлять все I ни автоматически обязательными, ни автоматически необязательными.
3. **Пройти все семь пользовательских путей и дорожную карту.** Проверить входы, actors/исполнителей, переходы, результат, ручное использование, обратную связь, ошибки и восстановление по существенности. Сопоставить STATE.N-01–N-08 с ними; различить общий план и проверку текущего Godot-проекта.
4. **Адресно проверить спорные утверждения и зависимости.** Использовать указанные первичные отчёты, релевантные настройки/исходники и при необходимости текущую официальную документацию Windows/Docker/Godot/GitHub. Безопасное read-only уточнение допустимо в пределах задачи; установка, запуск неизвестного кода, изменение прав и платные CI-действия сюда не входят. При недоступности evidence ограничить конкретный вывод.
5. **Собрать Findings и совместимые Proposals.** Проверить контрпримеры и альтернативные объяснения, отделить Problem/Risk/Uncertainty/Opportunity, назначить обоснованные приоритеты и gates. Поднять upstream-влияние, если меняется Scenario, цель или общий состав реализации.
6. **Сформировать единый полный review и краткий ответ.** Дать verdict именно по корректности выбранного плана, пояснить material находки и ограничения. При наличии связанных исправлений показать совместимый маршрут; не применять его молча к рабочему плану.
7. **Проверить и сохранить результат.** Использовать существующий owner, один читаемый Markdown и относящийся к нему локальный Git-коммит; выполнить diff/read-back, сохранить чужую работу. Разделить публикацию, semantic commit решений и фактические изменения runtime. Новая читаемая копия в forfiles и отдельный tracking-реестр не нужны.

Шаги 2–4 могут чередоваться по найденным зависимостям. Независимые чтения можно объединять. Несколько агентов и отдельная инфраструктура для этой проверки не требуются. Весь этот Execution Plan остаётся candidate; сейчас выполнена только подготовка.
