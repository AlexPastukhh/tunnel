# C-04: защита действующего Fortis Repo без отдельного Windows-профиля

**Candidate Pre-work / pending, не принят.** 25 октября 2026 года, Asia/Bangkok. Исходный checkpoint: `8c36817bd52f0f8c575c772b890a68902f4b3c07`. Текущие решения и история: [STATE](../STATE.md), [JOURNAL](../JOURNAL.md).

## Направление пользователя и предлагаемая единица

Пользователь уточнил: задача — определить защиту туннеля Fortis Repo. Через Repo ИИ выполняет разные виды работы в предоставленной среде; отдельный Windows-профиль для самого Repo сейчас не требуется. При ручном запуске результата пользователь может выбрать отдельную Windows-учётку для ограничения влияния на основные файлы либо основную учётку, если доверяет результату. Отдельная тестовая учётка не является обязательным этапом каждой итерации.

**Ближайшая единица:** составить проверяемую карту защиты нынешнего Fortis Repo и предложить минимальные достаточные изменения, если выявится конкретный пробел. Результат — один читаемый отчёт: ресурс/маршрут → доступ агента и кода внутри Repo → механизм ограничения → evidence → остаточный риск → предлагаемое действие и способ проверки.

Это подготовка к адресному read-only обзору. Текущий запрос и уточнение позволяют постановку/проверку готовности; полный обзор и применение изменений не объявляются выполненными. Проектный Godot-опыт не выбран ближайшим шагом.

## Что входит в проверяемую границу

| Поверхность | Что установить | Уже известный предел |
| --- | --- | --- |
| Данные | Какие области контейнер читает/меняет и какие записи сразу отражаются на Windows | Repos/Workfiles RW уже переданы; отдельная учётка последующего запуска не отменяет запись через Repo |
| Исполнение | Полномочия shell, тестов, зависимостей и другого запускаемого внутри Repo кода; ресурсы и остановка | MCP file allowlist не равен изоляции произвольного shell |
| Windows-компонент Repo | Разделить Windows launcher/bridge, Linux token и Docker/file-sharing/control | Запуск launcher из основной учётки не означает автоматического получения Linux-процессом всего Windows token; защита Windows-компонента требует собственного evidence |
| Управление | Доступность Docker/control interfaces, изменения доверенного bridge/launcher/config и секретов | Не читать значения секретов; доступность control plane не выводить из имени профиля |
| Сеть и передача | Разрешённый обмен и известные host/cloud маршруты | Отсутствие стандартного socket/PATH-команды не доказывает отсутствие всех альтернатив; сетевое сканирование не входит |
| Результат | Граница между работой/тестами в Repo и ручным Windows-запуском результата | Основной/тестовый аккаунт выбирает пользователь; функциональный успех не доказывает безвредность всего поведения |

Цели опираются на N-WF-01–03, все S-01–S-07 и существующие I-01–I-14 из [REQUIREMENTS](../REQUIREMENTS.md), с их прежним статусом. Новых глобальных FR и запрета всех host metadata не вводится. Разнообразие задач не трактуется как поручение искать или читать любое содержимое широких mounts.

Используется прежняя модель угроз: ошибки агента, недоверенные инструкции, компрометация инструмента/подключения, риски зависимостей/исполняемого кода; для неизвестных локальных ИИ также их runtime. Отдельная учётка Windows-запуска решает свою задачу после выдачи результата и не заменяет защиту среды Repo.

## План, проверка и gates

1. Зафиксировать target действующего Repo по доступным несекретным metadata. Переиспользовать уже достаточное evidence; исторические PID/config не выдавать за live.
2. Адресно сверить доступные настройки/метаданные mounts, identity, контейнерных ограничений, доверенного runtime/control и сети. Не читать payload, credentials, полные профили или посторонние проекты; не использовать Windows/G2 и не искать альтернативные подключения.
3. Сопоставить механизмы с доступом агента и кода внутри Repo. Для Windows-части, недоступной из Repo, явно указать gap; при существенности подготовить минимальную ручную проверку пользователю.
4. Для каждого material gap предложить простой достаточный вариант и влияние на S-01–S-07. Выбор дополнительной учётки для Repo не возвращать без нового конкретного основания.
5. Подготовить проверку достаточности мер. При необходимости тестов записи/отказа сначала определить синтетические объекты и положительный control; текущая единица не запускает пробы на личных данных и не применяет настройки.
6. Сверить выводы с WR/EA, сохранить отчёт у существующего owner и локально зафиксировать относящиеся документы. Push, runtime deploy/restart, ACL/mount/network changes и отключение подключений не входят.

**Readiness:** READY для предложения адресного обзора через существующий Repo. Недоступные Windows permissions и непроверенные альтернативные маршруты ограничивают будущие выводы, но не требуют отдельного профиля или Godot exe перед началом анализа. Состав C-04 ещё не принят как выполненный/внедрённый.

Cost: переиспользование текущей схемы уменьшает объём перестройки; адресный обзор требует анализа и проверки источников. Цена реализации/lifecycle определяется только для обоснованных мер. Новых сроков, бюджетов и обещаний полной изоляции нет. Полный review старого плана C-01 остаётся отдельной работой.
