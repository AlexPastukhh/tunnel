# Отдельный профиль, Fortis Repo и G2-туннель: польза и Candidate Pre-work

**Candidate / reading copy / not canonical.** Дата: 24 октября 2026 года. Источники текущего контекста: переписка пользователя и документация `tunnel` в версии `a17de42775d14b5f6ac0dad8b2e77665ca65ce40`.

Этот материал уточняет постановку работы перед дальнейшей настройкой и review общего плана. Выполнено ограниченное сравнение по источникам. Нового аудита Windows, запуска приложений, переноса Docker или отключения туннеля не выполняли. Ни сценарий, ни состав C-02 ниже не являются `BASELINE COMMITTED`.

## 1. Предмет и предварительный вывод

Пользователь хочет понять три разные вещи: нужен ли ChatGPT именно Windows/G2 Desktop Commander-туннель; полезна ли отдельная Windows-учётная запись для ручного запуска результатов; полезна ли отдельная учётка для обслуживания Fortis Repo.

**Предварительный вывод для выбора следующего шага:**

1. Среди установленных сценариев не выявлено потребности, которая требует именно общего G2 Desktop Commander-туннеля. Его возможная польза — автоматизировать Windows-действия агента. Такая автоматизация может быть нужна, но не обязана реализовываться этим туннелем.
2. Отдельная обычная Windows-учётка может быть полезна для ручной проверки своих приложений и игр с ограниченным доступом к личным ресурсам. Польза зависит от реальных прав, а удобство и совместимость нужно проверить на выбранном проекте.
3. Учётка для Windows-компонентов Repo — отдельный вариант защиты. Её польза зависит от того, какие процессы и доступы перенесены; перенос одного launcher и изменение контекста Docker/file-sharing нельзя считать одинаковой операцией.
4. Обычная учётка не является универсальной средой для свободного запуска предположительно вредоносных программ. Для более сильного отделения окружения рассматривается отдельная ОС — VM/Sandbox с ограниченным обменом.
5. Первым небольшим опытом предлагается ручной запуск известного Godot-проекта в существующей G2-учётке. Для этого не требуется сначала переносить Repo или добавлять Windows MCP.

Это вывод о назначении вариантов. Он не подтверждает готовность нынешней конфигурации или поддержку всех нужных функций.

## 3. Что установлено по источникам

### Доступ Windows и пример с реестром

[Microsoft Access Control](https://learn.microsoft.com/en-us/windows/security/identity-protection/access-control/access-control) описывает доступ по SID, правам и ACL объектов. Поэтому отдельная учётка может ограничить доступ приложения к ресурсам владельца, если соответствующие права действительно закрыты.

[Microsoft Registry Security](https://learn.microsoft.com/en-us/windows/win32/sysinfo/registry-key-security-and-access-rights) различает права чтения и изменения ключей. [Predefined Keys](https://learn.microsoft.com/en-us/windows/win32/sysinfo/predefined-keys) относит HKLM к машинной конфигурации, включая ПО, а HKCU — к текущему пользователю. Следовательно, запрет личных файлов не обещает скрыть доступную машинную конфигурацию.

Пользователь сообщил о чтении списка приложений через G2. Количества записей и обстоятельства того запуска здесь не перепроверялись; исходного поручения и полного tool-output нет. Этот пример поддерживает необходимость явно определить границу данных. Он сам по себе не устанавливает обход ACL, чтение профиля alexa или нарушение разрешения прошлого запроса.

Можно ограничивать конкретные ресурсы Windows отдельно. Однако запрет одного источника сведений не доказывает изоляцию всего окружения и может потребовать проверки совместимости. Для нынешней задачи нет обоснования сначала строить такую сложную Windows-политику ради сохранения необязательного общего shell-туннеля.

### Репозиторий и установленный Repo

По `docs/ISOLATION_GUIDE.md`, разделу «Отдельно о Docker и запуске Repo под alexa», датированная схема такова: Windows launcher под alexa → narrow runtime E38 → Docker exec → Linux MCP. Документ сообщает об удалении административной API-поверхности E38 и прямо отделяет Linux-процесс от полного Windows token владельца. Это историческое свидетельство; live cutover сегодня не повторялся.

Тот же документ оставляет риск компрометации Windows-компонента в контексте его учётки. Это конкретное потенциальное основание для дополнительного ограничения Repo-хоста; оно отличается от обычного выполнения команды внутри Linux-контейнера.

По предоставленному ранее inspect и [STATE](../STATE.md), в Repo переданы корни Repos и Workfiles RW. [Docker Bind Mounts](https://docs.docker.com/engine/storage/bind-mounts/) описывает предоставление host-пути контейнеру. Поэтому удаление G2-туннеля не заменяет решения о выданных Repo данных.

[Docker Windows Permissions](https://docs.docker.com/desktop/setup/install/windows-permission-requirements/) различает контексты Desktop/helper/file-sharing и описывает сохранение исходных разрешений разделяемых host-файлов. Вывод для нашей схемы условный: отдельная учётка может добавить полезное ограничение, если именно её права реально определяют соответствующий файловый доступ. Один перенос launcher этого не доказывает. Текущий backend, установленная версия и полная цепочка полномочий отдельно не проверялись.

### Запуск непроверенного кода и роли аккаунта

[Microsoft Access Tokens](https://learn.microsoft.com/en-us/windows/win32/secauthz/access-tokens) описывает выполнение операций в контексте token процесса. Практическое следствие: если обычный процесс учётки читает ключ Repo или изменяет launcher, другой обычный процесс с эквивалентными правами этой учётки тоже может получить такой доступ. Нельзя автоматически считать аккаунт одновременно безопасным местом для недоверенного кода и владельцем инфраструктурных секретов.

[Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/) использует отдельное ядро через виртуализацию; окружение временное. Это другой уровень отделения, чем аккаунт той же Windows. Сеть включена по умолчанию, поэтому обмен с хостом и сеть требуют явного рассмотрения. Совместимость нужной игры, GPU/устройств и ресурсы на этом компьютере не проверены.

## 4. Для чего полезна каждая роль

| Роль | Наблюдаемая польза | Ограничение и цена |
| --- | --- | --- |
| Отдельная неадмин-учётка для ручной проверки | Пользователь запускает игру/приложение, не выдавая ему автоматически права основного пользователя на личные папки; рабочее состояние приложения отделено по доступным ему ресурсам | Остаются разрешённые общие ресурсы Windows, выданные папки и сеть. Переключения, инструменты, доступ к проекту и функции нужно проверить |
| Отдельная учётка для Windows-части Repo | Возможное уменьшение последствий компрометации Windows-компонента; при соответствующей схеме — дополнительное ограничение файлового обмена правами Windows | Необходима карта реальных identities и Docker-прав. Возможны настройка запуска, ключей, доступа к данным и восстановления. Польза не доказана одним новым именем пользователя |
| Windows/G2 Desktop Commander-туннель | Агент сам выполняет Windows CLI/GUI-задачи, получает результаты и повторяет проверки | Даёт агенту прямой Windows-интерфейс. Для ручной проверки пользователя не требуется. При отказе нужно отдельно обеспечить нужную автономность Windows-only тестов |
| VM/Sandbox для недоверенного запуска | Отдельное окружение для кода, которому нельзя доверять доступные обычному пользователю сведения/ресурсы основного Windows-хоста | Настройка передачи результатов, ограничения интеграции и потребление ресурсов. Не обещана полная пригодность для любых игр/устройств |

Пример пользы обычной тестовой учётки: ошибка приложения пытается удалить файл в закрытой для неё папке владельца — обычный файловый доступ должен получить отказ. Выданный ей проект всё ещё может быть повреждён; восстановление проекта рассматривается отдельно. Этот пример иллюстрирует механизм, а не выполненный здесь тест.

Пример предела: программа под G2 запрашивает разрешённые машинные ключи Uninstall. Разделение личных профилей не обещает отказа. Отсутствие MCP убирает прямой канал таких запросов ChatGPT, но не запрещает их автоматически программе, которую пользователь сам запустит в G2.

**Отдельный профиль полезен как ограничение последствий, но не является автоматическим допуском всего кода к запуску.** Функциональная проверка конкретной версии не доказывает её безвредность в более привилегированной среде. Ручную проверку можно продолжать в выделенной среде; переход в основной профиль не обязан быть этапом каждой итерации.

## 6. Candidate Desired Real-Life Scenario: ручная проверка Windows-результата

**Статус:** candidate/inferred, scope — первый известный проект. Это подробная реконструкция одного пути S-01/S-02, а не принятая новая DRLD и не отдельная база требований.

**Fundamental Benefit:** пользователь реально проверяет своё приложение/игру в подходящей Windows-среде, сохраняя выбранное ограничение доступа к личным ресурсам. Польза возникает при доступной ручной проверке и повторяется при следующих версиях.

**Scenario Concept:** агент разрабатывает в Repo; пользователь запускает конкретный результат в обычной тестовой учётке и передаёт необходимую обратную связь. Прямой Windows Desktop Commander для этого пути не используется.

**Detailed Desired Real-Life Scenario:**

1. **Условия/входы:** выбран собственный Godot-проект или его тестовая сборка; определена версия; пользователь имеет тестовый login. Нужный Godot/исполнитель доступен в этом контексте. Наличие и путь exe пока не подтверждены.
2. **Trigger:** готова версия для ручной проверки. Для одного сравнительного опыта агент не меняет её незаметно во время теста; это не глобальный запрет живых итераций.
3. **Подготовка:** агент сообщает расположение результата, способ запуска, ожидаемые функции и необходимые команды. Если нужны host-настройки, пользователь применяет их вручную по отдельным подготовленным инструкциям.
4. **Переход к исполнению:** пользователь входит в обычную тестовую учётку и запускает выбранный результат. Используется уже допустимый fallback с переключением профиля; отдельный экранный bridge пока не строится.
5. **Точка пользы:** пользователь проверяет ввод, изображение, звук и другие функции выбранного проекта. Фиксируются конкретная версия, фактический успех и ограничения.
6. **Обратная связь:** пользователь сообщает нужный результат/лог или сохраняет выбранный артефакт в доступную Repo область. Не требуется открывать весь рабочий стол/профиль владельца.
7. **Следующая итерация:** агент исправляет проект, затем проверяется следующая определённая версия. Недоступная функция, неудобный обмен или слишком большой ручной труд становятся основанием пересмотреть маршрут.
8. **Исключения/восстановление:** если инструмента нет, готовятся ручные действия; если маршрут несовместим, выбирается другой исполнитель с сохранением требуемых функций. Для тестового результата используется восстанавливаемая версия/копия при необходимости; обязательное дублирование всех репозиториев не вводится.

Принятого SRU-дерева в текущих источниках для этого пути не установлено. Его минимальная candidate realization composition: доступный проект/инструмент → ручное исполнение/проверка → выбранная обратная связь. Она покрывает этот опыт, но не объявляется полной реализацией всех S-01–S-07.

## 7. Затраты и почему достаточно небольшого опыта

| Поверхность | Достаточная оценка сейчас |
| --- | --- |
| Scenario operation cost | Переключение профиля, запуск и возврат обратной связи. Пользователь сообщил ориентир около минуты на переключение; частота Windows-итераций и остальные длительности неизвестны. Их надо наблюдать, а не считать число шагов доказательством удобства |
| Realization/delivery cost | Учётка и узкий доступ к проекту уже существуют. Путь Godot, import/renderer и ручной цикл ещё не проверены. Нужна адресная подготовка, а не новая система туннелей. Перенос Repo/Docker имеет другие зависимости и не входит в этот опыт |
| Lifecycle/future-option cost | Потребуются поддержка нужных инструментов и восстановление. Новый launcher/runner, VM или отдельный Repo-аккаунт могут добавить ценность, но также поддержку и новые границы. Не реализовывать их только ради возможного будущего |

**Сравнение:** сохранить весь текущий G2 MCP-путь — меньше отказа от существующей инфраструктуры, но остаётся ненужный выбранному ручному маршруту Windows-доступ ChatGPT. Ручной тест на существующей учётке даёт знание о реальной пользе/неудобстве без переноса Docker. Полный перенос Repo сейчас затронул бы identities, доступы и запуск до подтверждения его конкретной пользы. VM/Sandbox проверяет другую силу границы и может потребовать другого ресурса/совместимости.

Количество уже потраченных усилий не является самостоятельным основанием сохранять активный туннель. Наличие существующей учётки уменьшает объём следующего опыта. Количественная delta, бюджет, deadline и рассчитанный slack неизвестны; hard deadline не задан. Не делаются оценки по часам, стоимости и FPS.

## 11. Candidate Verification, Resolution Route и readiness

Материальные положительные оси будущей проверки: реальная ручная польза; сохранение FR и actor; достаточность входов/инструмента; доставка обратной связи; version binding; затраты повторного использования; отсутствие расширения тестовых полномочий. EA — исходные механизмы сбоев, не предел поиска осей.

Достаточные методы: адресный осмотр выбранной конфигурации и версии, пользовательская функциональная проверка, выбранный лог/артефакт, сравнение действий с WR и записью результата. Ранее выполненные ACL/file-тесты переиспользуются в их scope; они не обнуляются без изменения условий и не расширяются до полного PASS.

Если нужна новая проверка границы данных из-за изменившейся identity/ACL, использовать собственные синтетические объекты и положительный control. Не читать реальные личные файлы, не повторять инвентаризацию программ и не строить всеобщий security scan. Новый Windows-компонент или расход не становится допустимым только потому, что помогает тесту.

| Граница решения / этап | Prerequisites и gate | Проверяемый outcome |
| --- | --- | --- |
| Транзакция C-02 | Пользователь принимает точный состав одного ручного опыта; сценарий и WR/EA остаются candidate до этого | Определены границы следующего действия; все семь общих сценариев не сокращены |
| Подготовка/исполнение опыта | Доступны выбранная версия, обычная учётка и нужный Godot/исполнитель; шаги Windows выполняет пользователь | Реальный результат и цена ручного пути, а не новый общий security PASS |
| Следующие решения | Evidence опыта; при сильной модели угроз — выбор по F-U-03; при частых Windows-only тестах — F-U-04 | Отдельные candidate изменения маршрута, автоматизации или профиля Repo; они сейчас не принимаются авансом |

**Readiness: PARTIALLY BLOCKED для фактического ручного запуска.** Не подтверждены Godot exe/версия и полный путь исполнения проекта. Их можно установить подготовленными ручными шагами; они не блокируют концептуальное сравнение и подготовку команд. C-02 ещё не принят. Возможность VM и конкретная Repo-учётка не являются prerequisites первого опыта.

Перед завершением следующей работы проверить: target и actor; положительный outcome по WR; доказанность material выводов; неизменность полномочий; точность записей/read-back и ссылок. Пропущенное обозначать ограничением, не галочкой. Отдельного постоянного Axis Log не требуется.
