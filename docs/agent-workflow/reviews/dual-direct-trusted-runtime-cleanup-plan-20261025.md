# Trusted Tunnel/Bridge cleanup — owner decision, 2026-10-25

**Решение владельца (уточнение WF-046): не выполнять ручной перенос Tunnel сейчас.** Владелец разрабатывает отдельное локальное приложение для регистрации соответствия `Docker development source ↔ trusted Windows production installation`, запуска lint/tests/security review и явного одобрения ревизии с криптографическими хешами, а затем контролируемого копирования/установки на хосте из одобренной версии. Docker — недоверенная среда агентов; Windows-приложения запускаются только из проверенной копии вне agent-writable mounts. До готовности этого механизма **не переносить**, **не удалять**, **не останавливать** работающие Direct Repo; будущая очистка legacy Bridge является отдельным этапом после регистрации и безопасного восстановления.

## WF-046 — trust boundary для будущего локального promotion app

- Подход: source/test в Docker (без production key); доверенный Windows runner/updater, approved manifest/hash store, production files, runtime profiles и secrets — за пределами Docker, с Windows ACL, не доступными агентам на запись. Агент может **предложить**, но не может самостоятельно утвердить/запустить release или изменить approved manifest; проверки lint/tests не заменяют review злоумышленного кода.
- Проверять хеши всего релизного набора/зависимостей и файлов после export/copy/staging **на стороне доверенного хоста**; учитывать symlink/junction/hardlink/TOCTOU, manifest/approval независимо от agent-controlled volume, identity approver и safe rollback. Production promotion допускается только явным согласием владельца или доверенной отдельной политикой, не исходя из результатов, которые может подменить агент в Docker.
- Важно: исходник в Docker может тестово исполняться, но должен быть **неспособен получить настоящую рабочую identity/credentials, изменить хостовые production файлы или неавторизованно вызвать update API**. Просто не класть `runtime.key` в Docker полезно, но **недостаточно**, если host management/runtime endpoint доступен без аутентификации; F-R-06 network audit остаётся.
- **Текущий Tunnel частично уже соответствует**: Windows trusted startup scripts первого и второго вне обычных Docker mounts, Windows EXE вне Repos/Workfiles, первый `runtime.key` имеет защищённую Windows DACL для alexa; второй KeyFile/profile и все indirect aliases требуют read-only проверки. Linux Direct DC внутри Docker — **не production Windows Tunnel copy**, а необходимый MCP backend; не делать его «неработающим» просто ради этой модели. Legacy Bridge лежит в Docker RW, но не исполняется двумя действующими Direct.
- **Непокрытый риск:** Windows `C:\Tools` имеет Authenticated Users Modify; для G1 есть Deny, CodexSandbox accounts существуют, эффективные права разных токенов не доказаны. Конечная интеграция с promotion app должна обеспечить неподменяемый production path/loader/ACL и сохранение maintenance прав alexa. До регистрации и готового безопасного rollback ничего не переносить.

## Приоритетный обнаруженный Windows ACL gap — WF-041

Owner read-only по обоим закреплённым EXE: `Get-AuthenticodeSignature` = **NotSigned**, на самих файлах найдено по **одной** broad write-type `Allow` ACE, на каждом предке (включая `C:\Tools`) **по две**; broad `Deny` = 0, неразрешённых SID = 0, reparse = false. Это **не доказывает эффективный доступ произвольной учётки**: нужен список конкретных ACL прав, применимости ACE, targeted Deny и actual access check под соответствующим token. NotSigned не доказывает вредоносность; прежние hash pins Client/Runtime совпадают, но независимой publisher attestation нет. **Не менять ACL на работающей системе до адресного плана и контролируемого восстановления**; не объявлять Windows trust boundary защищённым только на основании SHA. Риск F-R-07 остаётся приоритетным.

## Дополнение WF-042: защита ACL без блокировки `alexa`

Owner ACL counts для Client/Runtime EXE и каталогов `C:\Tools`, `tunnel-client`, `runtime/v0.0.15`: `InheritanceProtected=False`, `AlexaAllowWriteACE=0`, `SYSTEM=1`, `Administrators=1`, broad Authenticated Users Write Allow=1, прочих Write Allow=0. Нельзя удалять Authenticated Users Modify вслепую: обычная сессия `alexa` может лишиться возможности обслуживать Tunnel. Не следует делать массовый ACL reset на общем `C:\Tools` или корне `C:\`. Сначала owner read-only проверяет фактических владельцев, состав токена, наследование и права Delete/DeleteChild на файлах **и предках**, затем согласует узкий secure root, явные права `alexa`, SYSTEM, Administrators, RX потребителей и независимый ACL backup/restore. Microsoft Win32 `DeleteFile` подтверждает, что для удаления/переименования достаточно DELETE на объекте либо DELETE_CHILD у родителя. Только потом адресное изменение Windows с rollback, без остановки двух Repo до согласованного окна.

## Порядок проверки и безопасной очистки

1. **Проверить всю цепочку исполнения и доверия**: Windows launcher/control/guard, `$Client` и `$Runtime`, `docker.exe` PATH, Linux node/DC, разрешения файлов и их предков, effective Windows ACL, junction aliases. Проверка только безопасной метаинформации без вывода профилей/ключей.
2. **Проверить профили/автозапуск без утечки секретов**: какие сохранённые MCP commands используют Direct или Bridge; найти оставшиеся legacy references (Bridge/probe) и их consumers, отличая исполняемый runtime от копий исходников/документации в Git. Trusted launchers/keys и исполняемые зависимости должны быть ВНЕ agent-writable paths.
3. **Выбрать достаточную модель угроз**: защита от случайных/злонамеренных изменений UID1000, других Windows учёток, сетевых сервисов; закрыть или явно принять F-R-06 network, F-R-07 Windows path ACL и RW shared-config. Для независимости профилей потребуется раздельный container/UID/volume/mounts.
4. **Проверить безопасный reboot/rollback** до любой очистки: после сброса tmpfs restore pinned DC/Git, запуск каждого профиля, совместная работа 2 Direct, 0 Bridge, возможная гонка одновременного холодного старта и повторный запуск fail-closed. Создать восстановление Direct БЕЗ зависимости от Bridge из RW каталога; ключи/восстановление хранить в доверенном месте.
5. **Согласованный адресный вывод legacy**: список exact paths + consumers/ownership/backups; архив вне agent-writable locations с SHA/ACL; затем разрешённое владельцем удаление `/workspace/repo/.fortis/mcp-bridge.mjs` и иных точно идентифицированных ненужных runtime-копий. Не делать слепое `rm -rf` или удаление всей `.fortis`/Git worktree: возможно присутствие иных consumers/данных. Источники в Git можно оставить для разработки лишь если они не исполняются доверенной цепочкой; владелец может предпочесть их отдельный архив вне доступных roots.
6. **Повторный приемочный аудит**: Windows installed hashes+effective ACL, отсутствие startup refs на legacy Bridge, live process census, exact RW path check, оба actual-client smoke, controlled reboot, rollback без Bridge, документированный список остаточных рисков.

**Статус:** пока только план; два Direct MCP продолжают работать. Полной / абсолютной гарантии безопасности нет. Критерий достаточности — в согласованной модели угроз trusted startup/keys не достижимы UID1000 на запись, нет зависимостей от legacy Bridge, recovery Direct независим, документированы принятия для общего доступа/сети.
