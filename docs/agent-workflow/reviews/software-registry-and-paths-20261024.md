**Evidence Gap:** физические расположения большинства программ и их effective file permissions для G2 пока неизвестны. Записи реестра не заполняют этот пробел.

## Почему список был виден

В описанном сборе названия/версии/издатели 125 записей получены из uninstall-ключей реестра. Для этого не требуется открывать каталоги каждой программы. Версии Fortis из метаданных файлов/конфигурации — другой источник; его нельзя переносить на весь список.

По [Microsoft Registry Key Security](https://learn.microsoft.com/en-us/windows/win32/sysinfo/registry-key-security-and-access-rights) чтение ключей определяется их security descriptors и отдельными правами. По [Access Control Overview](https://learn.microsoft.com/en-us/windows/security/identity-protection/access-control/access-control) файлы/папки и registry keys — разные объекты доступа.

Следствие: даже запись о программе, чьи файлы закрыты для G2, может читаться из разрешённого ключа HKLM. И наоборот, запрет registry key не устанавливает запрета чтения файлов программы. По одной Machine64/Machine32-записи нельзя заключить, находится ли приложение в Program Files, в папке alexa или в другом месте и может ли G2 его запустить.

**Настраивать доступ к конкретным ключам реестра можно.** Это не невозможное свойство Windows. Но обычное создание отдельного аккаунта не означает такого запрета; закрытие отдельных Uninstall-ключей также не доказывает сокрытие программы из всех иных источников. Изменения ACL здесь не предлагаются к немедленному применению.

## Контекст требований и текущая граница

User Need — ограничить данные/действия агента и сохранить удобную разработку/ручную проверку. Прямое ограничение — настройки Windows выполняет пользователь вручную. Сохраняется различие между Repo/Docker и Windows/G2 DC.

Пользователь в последнем сообщении описал текущий вариант: Repo остаётся как есть, а основной или тестовый аккаунт для запуска выбирает сам пользователь. Это уточнение направления; техническое перенастраивание и принятие всех прежних C-01/C-02 из него не выводятся. Успешная проверка в тестовом аккаунте не является автоматическим доказательством безопасности owner-запуска.

Для этой адресной работы отдельные DRLD/SRU-дерево не требуются: она уточняет входы и границы существующего workflow. Прошлое чтение uninstall не объявлено нарушением без исходного поручения и ранее действовавшей классификации данных.

## Следующий минимальный сбор — PR-A-05

**Origin: assistant; status: selected candidate.** Предлагается один ручной read-only сбор тех же трёх uninstall-источников под FortisHostG1 с пятью полями: DisplayName, DisplayVersion, Publisher, InstallLocation, DisplayIcon. Он устраняет нехватку зарегистрированных путей, не открывая личный HKCU alexa и не требуя Windows-туннеля ChatGPT.

Подготовлен [Read-SoftwareLocations.ps1](../tools/Read-SoftwareLocations.ps1). Открыть файл, проверить содержимое и вручную вставить его целиком в обычный, не повышенный PowerShell под `FORTIS_M\FortisHostG1`. Скрипт выведет JSON; передать результат в чат выбранным пользователем способом.

Скрипт открывает ключи read-only и читает только перечисленные значения. Он не запускает приложения/деинсталляторы, не читает UninstallString, не сканирует диск, не открывает файлы программ, не записывает реестр/файлы и не меняет подключения. Неверная учётка или повышенный token приводят к остановке. Ошибки отдельных ключей включаются в Failures; отсутствующий ключ не объявляется DENY.

По [Microsoft Windows Installer Properties](https://learn.microsoft.com/en-us/windows/win32/msi/uninstall-registry-key) InstallLocation — зарегистрированное значение, связанное с ARPINSTALLLOCATION. Оно может не дать искомого фактического пути. DisplayIcon — вспомогательная ссылка на ресурс и не принимается автоматически за основной каталог приложения. Переменные окружения в значениях сохраняются как записаны.

Сначала сопоставить результат с исходными строками по имени/версии/scope, затем адресно проверять конкретные пути. Отдельно различать metadata/existence, чтение файла, запись и возможность запуска. Получение JSON ещё не завершает проверку всех этих прав.

Autonomy выбора этого небольшого способа: HIGH, поскольку он соответствует ручному Windows-маршруту и не меняет настройки. User Review Priority: NORMAL. Доступ к данным из этого сбора предоставляет пользователь своим ручным действием; новые общие разрешения не вводятся.

## Candidate WR / EA / Verification

| WR | Основание и критерий |
| --- | --- |
| WR-L01 | Искать сведения о расположении, а не расширять задачу до обновлений или полного профиля. Критерий: только выбранные uninstall-источники и указанные поля |
| WR-L02 | Соблюсти ручной Windows-маршрут и исходную G1 identity. Критерий: пользователь запускает сам, helper отказывает иной учётке/elevation; Windows DC не вызывается |
| WR-L03 | Разделить расположение, сведения реестра и права файлов. Критерий: каждое утверждение имеет тип evidence; отсутствующие пути/ошибки не выдаются за защищённость или успешный запуск |
| WR-L04 | Сохранить неопределённость/ошибки чтения. Критерий: Failures и scope присутствуют; число записей не подгоняется под 125; неполные ключи остаются явным ограничением |
| WR-L05 | Передать проверяемый результат и сохранить происхождение. Критерий: JSON содержит identity/time/registry key; сопоставление с вложением воспроизводимо; реальная запись документа проверена read-back |

EA-L01: Machine64/32 принято за папку установки → неверная классификация. Проверка: опираться на значения пути, затем на отдельную file-проверку.

EA-L02: пустой InstallLocation заменён «типовым» каталогом → выдуманная находка. Проверка: оставить unknown, использовать вспомогательный источник только с его статусом.

EA-L03: helper запущен под alexa/elevation → проверена другая граница. Проверка: guard identity/token и поля результата; не обходить отказ повышением прав.

EA-L04: читаемая запись или существующий объект принят за чтение/запуск программы → неверный вывод об ACL. Проверка: отдельный вопрос и метод для каждого необходимого права, без выполнения программ на этом шаге.

В положительную проверку также входят наличие нужных метаданных по конкретной строке, сохранение частичных результатов и отсутствие побочных изменений. После результата допускаются новые адресные оси; текущий список не является гарантией полного аудита.

Готово сейчас: разбор вложения, ограниченный поиск, объяснение независимости прав, подготовка helper. **PARTIALLY BLOCKED:** для получения реальных Windows-значений нужен ручной запуск пользователя. Из разрешённого Repo-доступа эти сведения не получены. После получения JSON можно продолжить независимое сопоставление без чтения файлов/запуска приложений.

Стоимость одного нового сбора оправдана отсутствующими полями пути; повторно собирать весь профиль, сканировать диск и проверять все ACL не требуется. Точных длительности/частоты/бюджета нет; количественная delta не рассчитана.

Поэтому helper проверен чтением кода и границ операции, но не разобран PowerShell parser и не исполнен на Windows; это ограничение проверки, а не PASS. Первое фактическое выполнение должно вернуть результат либо ошибку для коррекции. Исходное вложение не изменено. C-03 не объявлен принятым baseline.
