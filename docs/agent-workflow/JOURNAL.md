Зафиксированы S-01–S-07 и I-01–I-14 из [REQUIREMENTS.md](REQUIREMENTS.md): приложения, игры, изображения/3D, аудио, ручная настройка Windows, CI и Observatory. ## WF-002 — 2026-10-24: диагностика исполнителей

**Источник:** непосредственные read-only проверки Fortis Repo и G2.

Установлены аппаратные/ресурсные параметры, перечисленные в STATE. G2 работает как FortisHostG1 без обнаруженного admin token/членства Administrators. Команды G2 исполняются в Session 2 при активном основном профиле в Session 1. Прямой игровой/GUI-маршрут этим не проверен.

Docker version из G2 получил permission denied через `npipe:////./pipe/docker_engine`. Это не основание выдавать G2 полномочия управления Docker. Сам контейнер Repo остаётся доступным через его отдельный инструментальный маршрут.

**Результат:** выбран первый кандидат ручной Windows-проверки — существующий Godot-проект; сначала необходимо разрешить ему узкий файловый доступ.

## WF-003 — 2026-10-24: исправление источников mounts

**Первоначальная ошибка:** строка `C:\134` из get_config/Linux mountinfo была принята за реальный Windows Source. Это утверждение исправлено; оно не используется для новых команд.

**Авторитетный источник:** владелец выполнил `docker inspect c6d7be9fe6eb --format '{{json .Mounts}}'` и предоставил результат:

- `C:\Users\alexa\Repos` → `/workspace/repos`, bind RW.
- `C:\Users\alexa\Workfiles` → `/workspace/files`, bind RW.
- Docker volume `fortis-repo-workspace` → `/workspace/repo`.

**Результат:** дополнительный mount для проекта, уже расположенного в Repos, сам по себе не нужен. Из G2 настоящие Repos, Workfiles и выбранный проект возвращали UnauthorizedAccessException. Их ACL также нельзя было прочитать от имени G2.

## WF-004 — 2026-10-24: подготовка и ручное изменение ACL

**Источник до изменения:** владелец предоставил icacls для Repos и проекта. У проекта были только CodexSandboxUsers RX, SYSTEM/Administrators/alexa FullControl; правила FortisHostG1 не было. Прямых Deny в показанных ACL не было.

**Проверка агента:** G2 не входит в CodexSandboxUsers; SeChangeNotifyPrivilege включён. Это позволило выбрать разрешение на конкретную подпапку без выдачи права листать Repos. Синтаксис подготовленного PowerShell-блока проверен parser без исполнения изменения.

**Действие владельца:** вручную добавлено `FORTIS_M\FortisHostG1:(OI)(CI)(M)` на:

`C:\Users\alexa\Repos\godot-projects\bl_jck_prj\bl-jck`

Перед grant владелец сохранил исходный ACL папки. Сообщённый путь резервной копии:

`C:\Users\alexa\AppData\Local\Fortis-bl-jck-acl-20261024-220023287.txt`

Команды владельца завершились успешно; итоговый icacls содержит новое Allow и прежние правила. Резервный файл не читался и не копировался в Git; его существование/содержимое агентом отдельно не проверялось.

**Откат именно этой добавки**, при соответствующем решении владельца:

```powershell
icacls 'C:\Users\alexa\Repos\godot-projects\bl_jck_prj\bl-jck' /remove:g 'FORTIS_M\FortisHostG1'
```

Команда отката здесь записана как процедура, не выполнена. До grant прямого Allow этого пользователя на корне проекта в предоставленном выводе не было. Последующие изменения ACL перед откатом нужно учитывать отдельно.

## WF-008 — 2026-10-24: предложение пользователя о ручном Windows/G2-маршруте

**Источник:** пользователь сообщил, что, по его мнению, туннель с широкими полномочиями G2 не нужен и предпочтительнее передавать ему команды для ручного выполнения.

**PR-U-02 — origin: user; status: pending; Proposal impact: UPSTREAM** относительно review общего workflow. Предложение меняет предполагаемый способ Windows-взаимодействия, сохраняя цели разработки и ручного использования результатов. Оно не превращено в FR и не принято автоматически на основании этой записи.

Конкретный candidate путь: разработка/проектные проверки агента в разрешённой Docker-среде → подготовленные агентом команды для Windows/G2 → ручное выполнение пользователем → необходимый результат/лог для следующей итерации. G2-аккаунт для ручного запуска и G2 MCP-туннель различаются; отказ от широкого туннеля сам по себе не устанавливает отказ от аккаунта.

**F-U-02 — Decision Uncertainty; UPSTREAM; disposition: unresolved.** Semantic target: полномочия и actor Windows/G2-действий общего workflow. Известно предпочтение ручных команд вместо широкого туннеля. Не установлено, исключает ли оно любые прямые Windows/G2-инструменты агента или оставляет узкий проектный маршрут. В первом случае Windows-проверки требуют передачи команд и результатов через пользователя; во втором возможна отдельная ограниченная автоматизация, чья необходимость и граница ещё не выбраны.

**User Review Priority: HIGH** — меняется регулярный рабочий путь и ручная нагрузка. **Intervention Priority: NEXT** — уточнить до зависимых Windows-этапов; hard deadline и немедленная необратимая потеря не установлены. Количественная cost/timing delta неизвестна: частота действий и расходы ручного обмена не измерены. **Decision Autonomy: USER_REQUIRED** для выбора границы: это пользовательский trade-off между автоматизацией и ручным контролем.

**Вопрос: partially blocking.** Блокирует выбор исполнителя прямых Windows/G2-действий и окончательное перепланирование N-02–N-04. Не блокирует Docker-разработку, подготовку ручных команд и фиксацию предложения. **Next Gate:** пользователь уточняет допустимость узкого прямого доступа; затем пересматривается зависимая candidate composition. Само уточнение не означает отключение действующего runtime.

**Фактически сделано:** предложение и открытая развилка добавлены в STATE/JOURNAL; REQUIREMENTS и прежний snapshot C-01 сохранены. Новое сообщение — более поздний вход, а не автоматическое доказательство дефекта старого плана. Windows/G2 не вызывался; подключения, ACL, mounts и runtime не менялись.
