# Сценарии и инварианты

Зафиксировано: 24 октября 2026 года, Asia/Bangkok. Основание — требования пользователя в текущей инициативе. Реализация может меняться; изменение требования фиксируется явно в JOURNAL и отдельном Git-коммите.

## Цель

Агенты самостоятельно разрабатывают и проверяют результаты в предоставленной среде. Пользователь удобно открывает результаты, запускает приложения, играет, осматривает 3D и слушает аудио. Доступ к остальным данным и настройкам компьютера остаётся ограниченным.

Для облачных моделей исходные угрозы — лишний доступ, ошибки, неподходящие команды, инструкции из недоверенных материалов и компрометация подключения. Для неизвестной локальной ИИ-сборки учитываются также намеренно нежелательное поведение модели и вредоносный загрузчик/рантайм. Доверие к модели не заменяет системных ограничений.

## Обязательные сценарии

| ID | Возможность | Критерий поддержки |
| --- | --- | --- |
| S-01 | Разработка web, Windows, CLI и других приложений | Агент читает/меняет файлы, устанавливает необходимые зависимости, собирает и тестирует; пользователь вручную проверяет нужные функции конкретной версии |
| S-02 | Разработка игр | Агент работает с кодом, сценами и ресурсами; пользователь может поиграть и проверить нужные проекту ввод, графику, звук, режимы окна и устройства |
| S-03 | Изображения и 3D | Агент использует MCP/графические инструменты; пользователь получает предпросмотр и экспорт, а при необходимости открывает редактируемый проект в подходящей среде |
| S-04 | Аудио | Агент создаёт/обрабатывает звук; пользователь слушает, перематывает, сравнивает версии и при необходимости открывает рабочий проект |
| S-05 | Настройка Windows-хоста и пользовательских профилей | Агент готовит точные команды, последствия, проверку и при необходимости откат; пользователь исполняет команды вручную |
| S-06 | Удалённые сборки/проверки, включая GitHub Actions | Агент получает логи и реальные артефакты конкретного run/commit и использует их для исправлений; права, данные, стоимость и ограничения CI известны |
| S-07 | Observatory и другие потребители данных агента | Данные автоматически принимаются и отображаются; управляющие действия имеют отдельную авторизацию; входное событие не становится произвольным кодом с правами владельца |

Для S-01/S-02 скриншот и успешный CI не заменяют интерактивную ручную проверку. Для конкретной целевой платформы нужен соответствующий исполнитель.

## Принятые предпочтения

Уточнение пользователя 25 октября 2026 года:

- Для самого Fortis Repo отдельный Windows-профиль сейчас не требуется: сохраняется текущая схема работы с разными видами задач в предоставленной среде. При ручном Windows-запуске результата пользователь выбирает отдельную тестовую учётку для ограничения влияния на файлы основной учётки либо основную учётку, если доверяет результату. Отдельная учётка запуска не обязательна для каждой итерации.

- Предпочтительно оставаться в основном Windows-профиле и оттуда видеть выделенную среду и управлять ею. Переключение в G2 допустимо как запасной путь; пользователь оценивает его примерно в минуту. Это не измеренный норматив.
- Желательно сократить повторный ввод длинного пароля, сохранив аутентификацию и границы доступа. Автоматический вход не является обязательным условием всей схемы.
- Необходимые проектные файлы и инструменты должны быть доступны в контейнерной среде. Недостающие данные агент запрашивает конкретно; зависимости может устанавливать внутри разрешённой среды в рамках задачи.
- Добавление host-папок, Windows-прав, драйверов, служб или изменение доверенного runtime — отдельное действие по S-05. Для Windows-проверки нужный проект или сборка передаётся ограниченному Windows-исполнителю.
- Ручная проверка должна ощущаться как обычный цикл «написал → запустил → проверил» для выбранного проекта. VR или специальная периферия не объявляются уже необходимыми: потребность определяется реальным проектом.
- Работа с общей исходной папкой допустима. Отдельная копия нужна там, где требуется фиксированная версия или иная граница исполнения; обязательного дублирования всех репозиториев нет.

Уточнение пользователя 26 октября 2026 года — практическая достаточность:

- Сохранить загрузку необходимых инструментов/зависимостей и разработку/исполнение недоверенного кода внутри Docker. Возможность скачать вредоносный компонент сама по себе не является основанием отключать интернет; Windows-код владелец без проверки не запускает.
- Ключи/credentials и важные данные владельца должны быть недоступны коду из Docker через реальные FS/mount/alias, окружение, конфиги, логи, forwarded agents и сервисы. Передача сознательно выданных несекретных development-данных не является самостоятельной причиной строить DLP/общий запрет egress. Это целевое условие, а не уже установленный факт отсутствия всех секретов.
- Проверить возможность получить Windows-полномочия через доступные вызовы/API, в том числе действие сервиса на собственных credentials без передачи ключа в Docker. Сама TCP/health-доступность сервиса не равна нарушению; важны доступные данные и действия.
- Код из Docker не должен штатно ослаблять реальные средства своей изоляции: Docker control, mounts/привилегии, host firewall/ACL, trusted launcher/updater/approval. Редактируемый dev/MCP-конфиг не считать независимой OS-защитой.
- Приоритет: сначала экспозиция ключей/важных данных, затем связанные host/API-полномочия и защищённость самих средств изоляции. Порча выданного workspace и исчерпание ресурсов также учитываются через независимое восстановление/лимиты; ручной отказ запускать Windows dev-копию этого не предотвращает.

## Инварианты

| ID | Требование |
| --- | --- |
| I-01 | Все S-01–S-07 имеют явный маршрут; готовность подтверждается по конкретному сценарию |
| I-02 | Пользователь удобно получает результат без аудита каждого файла и постоянной перенастройки доступа; просмотр из основного профиля предпочтителен, переключение допустимо |
| I-03 | Агент автономно меняет файлы, устанавливает разрешённые проектные зависимости, собирает и тестирует внутри выделенной области |
| I-04 | Предоставлены необходимые проектные данные и ресурсы; недостающий доступ запрашивается, а личный профиль и чужие проекты не открываются по умолчанию |
| I-05 | Для модели, инструмента, редактора и приложения известны среда и полномочия исполнения; недоверенный код не запускается под владельцем по умолчанию |
| I-06 | Просмотр экспорта, открытие исходного проекта, исполнение кода и установка компонентов имеют подходящие отдельные маршруты |
| I-07 | Данные агента не расширяют его права, не подменяют доверенный обработчик и не запускаются автоматически с полномочиями владельца |
| I-08 | Настройку Windows-хоста и пользовательских профилей пользователь выполняет вручную; другой канал не применяется для скрытого автоматического исполнения |
| I-09 | Результаты различимы по версиям; есть способ восстановления вне контроля рабочего агента |
| I-10 | Существенная ручная приёмка относится к фиксированной версии, которую агент не меняет незаметно во время проверки |
| I-11 | Различаются сообщение агента, exit code, лог, настоящий артефакт, наблюдённая отправка и ручная проверка; доказательство одной среды не переносится автоматически на другую |
| I-12 | Ограничения обеспечиваются реальными правами и изоляцией независимо от послушности модели; у неизвестной локальной сборки ограничивается также рантайм |
| I-13 | Подключения имеют различимые отзываемые полномочия; предусмотрены остановка и лимиты ресурсов, данных и CI-расходов |
| I-14 | Ручная проверка поддерживает нужные конкретному проекту функции: ввод, изображение, звук, файлы, сеть, GPU и устройства; неподходящий маршрут заменяется подходящим |
| I-15 | В целевой схеме неподконтрольный агентам Docker-source/тесты не становятся рабочей Windows-версией автоматически. Отдельный доверенный Windows promotion app регистрирует source↔installed paths, проверяет release по одобренному manifest/hashes, ограничивает API/ACL/ключи и обеспечивает rollback. Агент может предлагать, но не может сам утверждать или устанавливать релиз; механизм и правила одобрения проверяются до использования |

## Границы толкования

- Туннель передаёт запросы, а доступ определяют его исполнитель, Windows/Docker, mounts, сеть и авторизация.
- Desktop Commander allowedDirectories не является изоляцией произвольного shell. Изменение Windows ACL не доказывает обновление файлового allowlist MCP.
- Read-only доступ сохраняет возможность читать и передавать данные. Возврат содержимого файла облачному агенту также является передачей данных.
- Окно в основном профиле может показывать программу, исполняемую в другой среде. Выбранный способ отображения не должен автоматически передавать весь диск, owner-credentials и постоянный общий clipboard.
- G2 — отдельная учётная запись Windows; она не равнозначна VM. Реальные права и пригодность для выбранной программы проверяются отдельно.
- Изображения, 3D и аудио различаются по виду результата: пассивный экспорт, SVG/HTML, DCC/DAW-проект, плагин и скрипт не получают одинакового доверия по одному расширению файла.
- Место хранения результата не делает его безопасным для исполнения владельцем. Успешный запуск в Docker или G2 не является таким допуском.

Проверенное состояние и конкретные следующие действия поддерживаются только в [STATE.md](STATE.md); история изменений — в [JOURNAL.md](JOURNAL.md).
