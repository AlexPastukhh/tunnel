# Работа с агентами: точка входа

Каноническая документация общей работы через Fortis Repo, G2, CI и локальные ИИ находится в этом каталоге Git-репозитория `tunnel`.

На Windows: `C:\Users\alexa\Repos\tunnel\docs\agent-workflow`.
В Fortis Repo: `/workspace/repos/tunnel/docs/agent-workflow`.

## Где что фиксировать

| Документ | Назначение |
| --- | --- |
| [REQUIREMENTS.md](REQUIREMENTS.md) | Пользовательские сценарии, инварианты и принятые предпочтения |
| [STATE.md](STATE.md) | Последний проверенный срез, ограничения и следующие действия |
| [JOURNAL.md](JOURNAL.md) | Последовательность решений, действий, проверок и откатов |
| Git history | Точные изменения документов и осмысленные коммиты отдельных этапов |

Ранние самостоятельные выгрузки из переписки являются исходными срезами. Оперативное состояние этой инициативы поддерживается здесь. Документы не заменяют действующие ACL, mounts и авторизацию.

## Порядок для нового чата

1. Прочитать корневой [AGENTS.md](../../AGENTS.md).
2. Прочитать [требования](REQUIREMENTS.md), затем [состояние и ближайший шаг](STATE.md).
3. Прочитать последние записи [журнала](JOURNAL.md); исторические команды не запускать как текущий план.
4. Проверять живую конфигурацию адресно, когда следующий шаг зависит от неё. Не обнулять неизменные доказательства без причины.
5. Продолжить с ближайшего незавершённого пункта STATE; изменения Windows-хоста и профилей пользователь выполняет вручную.

## Рабочий цикл документирования

После каждого значимого решения или законченной проверки:

1. Записать в JOURNAL дату, цель, действие и фактический результат. Указать источник: пользователь, инструментальная проверка или вывод из наблюдений.
2. Обновить STATE: что теперь доказано, что остаётся неизвестным и какой следующий конкретный шаг.
3. Менять REQUIREMENTS только при уточнении пользовательских требований, сохраняя идентификаторы S-/I-.
4. Проверить ссылки, diff и отсутствие секретов в предназначенных для коммита файлах.
5. Создать отдельный локальный коммит завершённой логической правки. Одному шагу могут соответствовать несколько инструментальных команд; коммит на каждую команду не нужен.
6. В ответе сообщить результат, пределы проверки, SHA коммита и следующий шаг.

Запись в журнале не обязана хранить SHA собственного коммита: он однозначно виден в Git history. Не создавать дополнительные коммиты только ради такой самоссылки.

## Границы Git и публикации

- Перед изменениями проверить рабочее дерево и staged files. Включать в коммит только относящиеся к задаче пути; сохранять незавершённую работу других задач.
- Пользователь поручил осмысленную Git-фиксацию планов и документов этой инициативы. Push, изменение удалённых веток, force-push и публикация runtime выполняются по отдельному поручению.
- Сохранение, локальный коммит, push и применение Windows/Docker runtime — разные состояния. В STATE/JOURNAL отмечать только реально выполненное.
- В Git не помещать ключи, credentials, реальные профили подключений, дампы окружения, приватные upstream URL, полные payload-логи и резервные ACL-файлы.
- Ошибочное утверждение исправлять с сохранением причины коррекции в JOURNAL. Старое предположение не оставлять текущим статусом.

Пример темы следующего коммита: `docs: verify Godot launch under G2`. Тема описывает полученное изменение; запланированный запуск не оформляется как успешно выполненный.
