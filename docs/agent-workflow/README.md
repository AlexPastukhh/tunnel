# Работа с агентами и ведение документации

Это единственный протокол сопровождения документов репозитория `tunnel`. Он обязателен по [AGENTS.md](../../AGENTS.md). Документы описывают проверенное состояние, но не заменяют runtime, ACL, mounts и авторизацию.

## DRY, KISS и YAGNI

- **DRY:** изменяемый факт имеет одного владельца. Текущий статус исправлять на месте. Историческая датированная запись может сохранять прежнее значение со своим scope; она не становится ещё одной текущей сводкой. Короткое предупреждение рядом с опасным действием допустимо.
- **KISS:** текущая страница отвечает на свой вопрос прямо: что действует, что неизвестно, какой следующий шаг и где evidence. Не добавлять в STATE/runbook хронологию WF-этапов, старые NEXT и дополнения поверх противоречащего текста.
- **YAGNI:** использовать существующий plan, журнал и реестр. Новый handoff/review/архив создавать при самостоятельной задаче, отдельном доказательстве, явном запросе или необходимости сохранить вынесенную историю. Не создавать новый файл на каждый тест, сообщение или смену контекста.
- Полноту security-приёмки не сокращать ради объёма. Убирать повторные пересказы, а не требования, отрицательные результаты и пределы проверок. Для документирования достаточно Markdown и соразмерной проверки ссылок/diff; отдельный framework не требуется.

## Рабочий цикл — после каждого значимого шага

1. Найти владельца изменившегося факта. Прочитать актуальный файл и проверить рабочее дерево/индекс; учитывать параллельные правки.
2. Исправить текущую запись у владельца. Для Repo/Tunnel проверить влияние на V-/F-R-/P-, а на STATE — влияние на задачу или следующий gate. **Проверить все затронутые страницы обязательно; переписывать неизменившиеся страницы и дублировать факт в трёх файлах не требуется.**
3. Добавить короткую запись в журнал соответствующей работы: дата, основание, действие, наблюдение/результат, предел и ссылка на подробное evidence. В общем JOURNAL отражать решения и межпроектные/security изменения; обычные Checker code/test milestones остаются в его implementation log.
4. Поправить зависимый указатель или runbook, если он стал неверным. Существенные ограничения держать рядом с действием; команды истории не оставлять исполняемыми примерами текущей процедуры. При выносе истории сохранить текст и доступ к нему; Git history сохраняет версии правок.
5. Проверить diff, относительные ссылки и затронутые якоря, отсутствие секретов и чужих изменений; выполнить соразмерные проверки. Затем локальный коммит завершённого логического шага и краткий результат пользователю. Не откладывать документирование до конца проекта и не делать коммит на каждую команду.

## Как записывать доказательства

Для существенного утверждения достаточно найти дату/среду, actor или источник, точный scope/версию, наблюдённый результат и ограничение. Подробные команды/receipts хранить один раз у evidence, из реестра давать ссылку. Не добавлять пустые формальные поля к тривиальной правке.

- Различать сообщение владельца, наблюдение инструмента, source-only, Docker test, Windows test, installed release и реальное восстановление. `PASS(scope)` относится только к названной проверке; `OPEN/NOT_RUN/PENDING` не превращаются в PASS по предположению.
- Число тестов указывать с конкретным прогоном/логом и source checkpoint, если привязка установлена. Непривязанный или изменяемый лог не подтверждает будущую dirty revision. SHA фиксирует bytes, а не происхождение от производителя.
- Сохранять FAIL, отмены и причины исправления ошибок. История не переписывает прежний исход; текущий указатель исправляется, а старый этап помечается историческим. Новые риски/требования получают новые ID; старые не переиспользуются.

## Git и параллельная работа

Включать только собственные связанные пути. Перед полной перезаписью повторно проверить исходные bytes; при чужом изменении перечитать и согласовать содержимое, не затирать его. Сохранение, commit, push, deploy и restart — разные события; push/runtime-применение требуют отдельного поручения. Секреты, полные профили, приватные URL и raw payload/ACL backups в Git не помещать.

Обычно достаточно diff и read-back. При наблюдавшемся расхождении Git/file reads (F-R-14) дополнительно сравнивать явно прочитанные, staged и committed bytes; не скрывать отказ за «status clean». Запись не обязана содержать SHA собственного коммита — не создавать коммит ради самоссылки.

## Вход и передача контекста

Начать с AGENTS и [STATE](STATE.md), затем открыть владельца своей задачи и нужные evidence. Всю хронологию читать только для исследования истории или конкретного пробела. Для Tunnel обязателен текущий security-реестр; для Checker — его собственная точка входа.

Обычно handoff — ссылка на действующий STATE/plan плюс цель, ограничения и ближайший незавершённый gate. Новый чат продолжает текущую ревизию, не старый NEXT из исторического handoff. Предыдущие документы остаются историческими источниками, а не параллельным рабочим планом.
