# Работа с агентами: точка входа

Каноническая документация общей работы через Fortis Repo, G2, CI и локальные ИИ находится в этом каталоге Git-репозитория `tunnel`.

На Windows: `C:\Users\alexa\Repos\tunnel\docs\agent-workflow`.
В Fortis Repo: `/workspace/repos/tunnel/docs/agent-workflow`.

## Где что фиксировать

| Документ | Назначение |

| [TUNNEL_SECURITY_ISOLATION.md](TUNNEL_SECURITY_ISOLATION.md) | **Единый актуальный обзор безопасности двух Fortis Repo/Tunnel:** проверенные факты, открытые риски, Docker↔Windows граница, приёмочные тесты будущего локального updater/promotion app |
| [REQUIREMENTS.md](REQUIREMENTS.md) | Пользовательские сценарии, инварианты и принятые предпочтения |

Ранние самостоятельные выгрузки из переписки являются исходными срезами. Оперативное состояние этой инициативы поддерживается здесь. Документы не заменяют действующие ACL, mounts и авторизацию.

## Порядок для нового чата

1. Открыть корневой [AGENTS.md](../../AGENTS.md), затем [единый security/handoff Repo и Tunnel](TUNNEL_SECURITY_ISOLATION.md) (**начать с раздела 0**). Это действующий обзор, а не новая инструкция переустановки.
2. Прочитать [требования](REQUIREMENTS.md), затем верхний актуальный срез и RP-05/RP-06 в [STATE](STATE.md), после чего [последние записи JOURNAL](JOURNAL.md) WF-046 и новее. Более ранние этапы и их старые NEXT — история; не повторять как план.
3. Для работающего Direct учитывать [dual-install audit](reviews/dual-direct-postinstall-audit-20261025.md); для будущего Windows promotion app читать **отдельную** [текущую документацию Project Checker](../userscript-updater/README.md), [handoff](../userscript-updater/HANDOFF_CURRENT_V1_20261025.md) и [trust boundary](../userscript-updater/WINDOWS_TRUST_BOUNDARY.md). Source/DOCKER-TESTED ≠ установленный trusted updater.
4. Прежде чем зависеть от динамического факта, выполнить минимальный read-only контроль его live-состояния; старые PID и хеши — snapshots, не использовать их для stop/migration без новой проверки.
5. Продолжать с ближайшего **незавершённого** gate в STATE/security; Windows changes и профили — только owner-controlled, без неожиданной остановки двух Repo, Bridge fallback и ручного переноса.

## Обязательное активное ведение доказательств изоляции и безопасности

**Не откладывать до финального отчёта.** В каждом следующем чате при работе над Tunnel/Repo/Project Checker после любого значимого шага (успех, FAIL, отказ из-за guard, изменение исходника и release, изменение Windows/Docker trust boundary, новый риск, изменение решения владельца):

1. Проверить, изменяет ли новое свидетельство одну из строк **V-/F-R-/P-** в [TUNNEL_SECURITY_ISOLATION](TUNNEL_SECURITY_ISOLATION.md). Обновить дату, источник (`OWNER-REPORTED`, live MCP, source-only, app receipt), наблюдённое значение, границу вывода и остающийся риск. Для нового gate дать новый стабильный ID; старый FAIL не удалять.
2. **В тот же шаг** обновить [STATE](STATE.md): самый верхний актуальный срез, RP-05/RP-06, следующий безопасный gate. Новое installed/Windows PASS только после реального owner-readback; planned или Docker tests не равны release. Отдельные Project Checker code milestones принадлежат [его собственному журналу](../userscript-updater/IMPLEMENTATION_LOG.md), но изменения security boundary отразить и здесь.
3. Добавить датированный, хронологический факт в [JOURNAL](JOURNAL.md) со ссылками на исходные audits/receipts, scope, outcome и NOOP/rollback; сохранить старые факты с исторической маркировкой. Если текущий документ противоречит прежнему — **исправить текущий указатель**, а не переписать прошлое задним числом.
4. Пройти `git diff --check`, проверить относительные ссылки, отсутствие ключей/полных профилей/URLs, зафиксировать **только свои файлы** локальным коммитом (никакого push без разрешения). Если не удалось обновить что-то, прямо указать несинхронизированные документы как OPEN.

При передаче новому чату проверять, что **действующий MCP маршрут Direct**, а старые команды Bridge в ARCHITECTURE/OPERATIONS/handoff помечены legacy; запрещённое преждевременное действие — ручной перенос, удаление Bridge, массовое изменение `C:\Tools` ACL или restart двух Repo — не становится «next» автоматически.

## Рабочий цикл документирования

После каждого значимого решения или законченной проверки:

1. Записать в JOURNAL дату, цель, действие и фактический результат. Указать источник: пользователь, инструментальная проверка или вывод из наблюдений.
2. Обновить STATE: что теперь доказано, что остаётся неизвестным и какой следующий конкретный шаг.
3. Менять REQUIREMENTS только при уточнении пользовательских требований, сохраняя идентификаторы S-/I-.
4. Проверить ссылки, diff и отсутствие секретов в предназначенных для коммита файлах.
5. Создать отдельный локальный коммит завершённой логической правки. Одному шагу могут соответствовать несколько инструментальных команд; коммит на каждую команду не нужен.
6. В ответе сообщить результат, пределы проверки, SHA коммита и следующий шаг.

Запись в журнале не обязана хранить SHA собственного коммита: он однозначно виден в Git history. Не создавать дополнительные коммиты только ради такой самоссылки.

## Границы Git и публикации

- Перед изменениями проверить рабочее дерево и staged files. Включать в коммит только относящиеся к задаче пути; сохранять незавершённую работу других задач.
- Пользователь поручил осмысленную Git-фиксацию планов и документов этой инициативы. Push, изменение удалённых веток, force-push и публикация runtime выполняются по отдельному поручению.
- Сохранение, локальный коммит, push и применение Windows/Docker runtime — разные состояния. В STATE/JOURNAL отмечать только реально выполненное.
- В Git не помещать ключи, credentials, реальные профили подключений, дампы окружения, приватные upstream URL, полные payload-логи и резервные ACL-файлы.
- Ошибочное утверждение исправлять с сохранением причины коррекции в JOURNAL. Старое предположение не оставлять текущим статусом.

Пример темы следующего коммита: `docs: verify Godot launch under G2`. Тема описывает полученное изменение; запланированный запуск не оформляется как успешно выполненный.
