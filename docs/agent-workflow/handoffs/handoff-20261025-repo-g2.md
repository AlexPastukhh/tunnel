## 2. Что нужно пользователю

Пользователь хочет удобно получать и проверять результаты автономной работы агентов. Агенты должны разрабатывать, читать/писать проектные файлы, устанавливать разрешённые зависимости, собирать и тестировать. Пользователь должен иметь возможность открыть результат, запустить приложение, поиграть, посмотреть 3D или послушать аудио.

Одновременно нужно ограничить:

- доступ к данным, которые не выдавались для задачи;
- случайные вредные действия, неподходящие команды и последствия недоверенных инструкций;
- последствия компрометации инструмента/подключения;
- для неизвестных локальных ИИ-сборок — также намеренно вредное поведение модели и вредоносный runtime/загрузчик/пакеты.

Намеренное «восстание» ведущих облачных моделей пользователь предложил пока не рассматривать. Это не отменяет обычные ошибки, prompt injection и риск компрометации.

Пользователь отдельно попросил постоянно документировать сделанное и направление работы, использовать Git и осмысленные коммиты.

В прежних кандидатах используются Needs:

| ID | Смысл |
| --- | --- |
| N-WF-01 | Пользоваться полезными результатами автономной работы агентов |
| N-WF-02 | Ограничить лишнее чтение данных и нежелательные действия |
| N-WF-03 | Понимать состояние, направление и причины решений; сохранять историю |

FR-WF-01–04 в тех же кандидатах восстанавливают прямые условия пользователя: разработка/тестирование в выданной среде; полноценная ручная проверка; ручное применение Windows-настроек; необходимые входы/инструменты контейнерного этапа. Это не основание автоматически принять весь формальный baseline или придуманную архитектуру.

### Семь обязательных сценариев

### Практические предпочтения и ограничения

- Желательно работать из основного Windows-профиля и оттуда видеть/контролировать тестовый результат.
- Переключение в другой профиль допустимо. «Около минуты» — самооценка пользователя, не измеренный SLA.
- Повторный ввод пароля неудобен; автоматический вход или удалённый рабочий стол не приняты как обязательное решение.
- Нужные файлы и инструменты должны быть в предоставленной контейнерной среде. Если чего-то нет, агент конкретно просит входы/доступ либо устанавливает разрешённую проектную зависимость.
- Пользователь хочет проверять результат примерно как при обычном собственном цикле «написал → запустил → проверил».
- Нет подтверждённых hard deadline, бюджета, частоты Windows-итераций или обязательного VR/специального оборудования.
- Малая проверка одного проекта не сокращает общий scope до одного Godot-сценария.

null означает «не найдено в PATH», а не Windows ACL DENY и не полный поиск всех executable. Отсутствие стандартного socket не исключает любой TCP API.

Repo смог прочитать **наш уже сохранённый отчёт** с путями Brave/Edge/REAPER. Это положительный пример получения сведений из переданного файла, а не независимое чтение живого Windows inventory.

### Допустимый вывод

В проверенной обычной конфигурации Repo прямого маршрута для повторения Windows registry-сбора не обнаружено. Linux контейнеру нельзя автоматически приписывать весь доступ Windows-пользователя только потому, что его launcher находится на Windows.

Одновременно нельзя утверждать «через Repo невозможно получить эти 413 записей или любые сведения о программах никаким способом».

**Не проверены:** сетевые службы Windows и Docker TCP API; нестандартные sockets/executables/bridges; наличие всех экспортов/копий; symlink-цепочки; escape-векторы; все косвенные источники внутри Repos/Workfiles.

Установка Linux PowerShell сама по себе не создаёт Windows registry/API или Windows token. Получение данных из сохранённого JSON/документа, через специально предоставленный Windows API и прямое выполнение PowerShell на хосте — разные маршруты.

Последняя корректная формулировка ответа пользователю: **у Repo не обнаружен тот прямой Windows-доступ, которым воспользовались через G2; полная невозможность альтернативного получения данных не доказана.**

## 8. Архитектурные выводы и пределы

1. Registry ACL и filesystem ACL независимы. Читаемая uninstall-запись не доказывает чтение/запуск exe, а закрытая папка основного профиля не закрывает машинные ключи автоматически.
2. Чтение конкретных registry keys можно ограничить. Нельзя говорить, что Windows принципиально не позволяет это настроить. Закрытие одного источника не доказывает сокрытия всех следов ПО.
3. Отдельная обычная учётка полезна для разграничения прав при подходящих ACL, но не является VM и не обещает сокрытие всей системы.
4. Ручной ввод команды меняет контроль над исполнением/передачей результата. При том же effective token он сам по себе не уменьшает права команды.
5. Отказ от G2 убирает этот канал Windows-команд, но не удаляет переданные сведения и не сужает mounts Repo.
6. В Repo выданы целиком Repos/Workfiles. Это остаётся отдельной поверхностью данных; чтение каждого вложенного файла и минимальность выдачи не подтверждены.
7. Успешная функциональная проверка под G1 не является доказательством безопасности той же версии под owner.
8. Не надо автоматически объединять аккаунт для непроверенных сборок с владельцем ключей/launcher/Docker API Repo.
9. Исторические документы различают Windows launcher, Linux token и контекст Docker Desktop/file sharing. Перенос одного launcher не доказывает перенос всех identities/ограничение данных. Эти Windows-роли заново не проверялись.
10. Сейчас не требуется массово менять registry ACL или переносить Docker только ради найденного списка программ. Такие изменения — отдельные Proposals с конкретной пользой/ценой.

## 12. Как продолжать без потери цели

Это рекомендуемый порядок выбора следующей работы, **не новая принятая композиция**.

### Если продолжается текущий вопрос о границах Repo

1. Сначала точно сформулировать проверяемое утверждение: прямой доступ к живому Windows registry; косвенное получение metadata из файлов; возможность Windows-действий через отдельный интерфейс. Это разные утверждения.
2. Переиспользовать уже полученное evidence. Запуск команды, которой нет в PATH, ради ожидаемого command-not-found не докажет отсутствие всех других маршрутов.
3. Не обещать универсальное «получить невозможно». Если для решения нужен более сильный вывод, выбрать ограниченный набор интерфейсов/предпосылок и достаточный метод проверки; оставшееся обозначить limitation.
4. Проверку вести в существующей Repo-среде. Не подключать весь C:, Windows registry hives, Docker socket и новые host API ради теста.
5. Не возвращаться к G2 без нового конкретного запроса. Не искать ключи/credentials и не пробовать другие подключения ради обхода.
6. Граница выбранных данных должна учитывать содержимое Repos/Workfiles. Автоматическое сужение mounts сейчас не принято; если оно понадобится, предложить конкретную карту выдачи и оценить влияние на семь сценариев.

### Если следующий этап — реальная польза отдельной учётки

Подходящий малый кандидат уже есть в C-02: известный Godot-проект/фиксированная версия → подготовленные минимальные ручные Windows-шаги → реальный import/игра под выбранной обычной учёткой → обратная связь агенту → запись издержек повторной итерации.

До исполнения нужны Godot exe/версия, выбранные функции и надлежащий commit этой единицы. Новая VM/перенос Repo не являются обязательными prerequisites. Без новых данных не повторять marker smoke и не выдавать его за игру.

### Что ещё нужно выяснить по существенности

| Вопрос | Что он ограничивает |
| --- | --- |
| Считать ли host software inventory запрещёнными данными или главным образом защищать личные файлы/изменения? | Точный критерий конфиденциальности; пока не установлено глобальное FR «скрыть всё ПО» |

Не задавать все вопросы автоматически. Запрашивать только минимальный недостающий вход для выбранной следующей единицы, продолжая независимые части. Не спрашивать повторно, имел ли пользователь в виду профиль или Windows DC: это уже уточнено.

### Остальная дорожная карта STATE

STATE.N-01 — файловая часть DONE(scope); N-02 — определить Godot; N-03 — ручной import/игра; N-04 — удобный доступ из основной сессии; N-05 — зависимости/ресурсы по проекту; N-06 — web/media/3D/audio/local AI по сценарию; N-07 — CI по проекту; N-08 — Observatory как отдельный scope. Это старый рабочий маршрут, который нужно актуализировать относительно уточнённого ручного Windows-исполнителя, а не исполнять механически.

Исходный запрос «проверь план на корректность» остаётся без полного финального review. C-01 — только pre-work. Не объявлять его исполненным на основании последующих частных проверок.

## 13. Правила работы и документирования

### Полномочия и операции

- Разрешены осмысленные локальные коммиты относящихся документов. Push, merge/публикация, runtime deploy и перезапуск сервисов отдельно от этого.
- Windows-настройки/ACL/профили — точные команды для ручного исполнения пользователем. Не менять скрыто через иной канал.
- Проверки и проектная работа внутри разрешённой Repo-среды продолжаются в её scope; не просить подтверждения каждого обратимого чтения/редактирования.
- Не запускать неизвестные сборки под владельцем и не добавлять Docker authority тестовой учётке ради удобства file sharing.
- Не помещать в Git токены, runtime keys, credentials, полные профили подключений, приватные upstream URLs, payload-логи и ACL backup.
- После timeout мутации сначала проверить фактическое состояние, затем решать о retry.
- Не удалять Windows linked-worktree metadata из Linux из-за недоступного Windows-пути.

### Семантика, которую пользователь потребовал

Перед существенной новой единицей работы подготовить соразмерный **Candidate Pre-work Composition**. До разрешения этой единицы не выполнять её глубже постановки/планирования/проверки готовности.

- Различать User Need, Fundamental Requirement, committed decision, Proposal и Work Requirement. Идея пользователя сама по себе не становится FR или committed decision.
- Inferred Need/FR/Scenario явно помечать candidate/inferred.
- DRLD = Benefit → Concept → Detailed Desired Real-Life Scenario. Принятый сценарий нельзя придумать из текста ИИ. Рекурсивно декомпозируется реализация SRU, а не сам сценарий.
- WR — проверяемые требования текущей единицы; EA — механизмы будущего провала, не подтверждённые Problems.
- Finding Types: Problem, Risk, Decision Uncertainty, Improvement Opportunity. Evidence Gap отдельно.
- Различать User Review Priority, Intervention Priority, Decision Autonomy и disposition.
- Материальный вопрос привязывать к Finding/Proposal: что решает, blocking status, затронутый downstream и условие закрытия.
- Для связанных PR показывать совместимость, REQUIRES/conflicts, состав, порядок и gates. selected candidate не равен committed.
- Приёмка композиции атомарна внутри её реальной границы; выполненный узкий запрос не принимает авансом весь план.
- Cost: прохождение сценария, реализация и lifecycle отдельно. Не выдумывать сроки/бюджеты/проценты. Искать простой достаточный путь.
- Review Axes — план/исполнение проверок, а не само доказательство. Не считать отсутствие будущего теста дефектом завершённого review.
- Новые требования не делают старую работу ошибочной задним числом.
- Полный material результат в одном читаемом Markdown + краткий чат-ответ. Существующий owner имеет приоритет над новой копией в forfiles.

Большой исходный методический prompt целиком здесь не дублируется; существенные применимые правила сохранены. При появлении более точного нового пользовательского указания следовать ему с явной областью действия.

### Техника Fortis Repo

Использовать соответствующую skill fortis-repo-workspace, если доступна. На разовой ошибке инициализации MCP повторить одну безопасную проверку; перед retry записи проверить её эффект.

Команды выполнять из `/workspace/repo` с абсолютными путями. Работа Git-репозитория — по `/workspace/repos/tunnel`.

Для чтения/фиксации ранее использовали параметры Git:

```text
git --no-optional-locks -C /workspace/repos/tunnel \
  -c core.fsmonitor=false -c core.hooksPath=/dev/null \
  -c gc.auto=0 -c maintenance.auto=false ...
```

Сначала status/index; stage только свои пути; проверить cached diff/bytes; commit только относящихся файлов; read-back. Нельзя цеплять чужие изменения. Работа других чатов может появляться в любой момент.

Большие передачи текстов через shell нужно корректно quoting/при необходимости сжать. JSON.stringify не является shell escaping. Для JSON транспорта через Windows/Linux полезен ensure_ascii, чтобы не перепутать искажение кириллицы в канале с исходным содержимым. Одна такая read-transport ошибка в JOURNAL была исправлена до коммита; историческая запись не была семантически изменена.

Тон: понятный русский язык, прямо и без лести. Сообщать основной результат, доказательства и пределы. Не оставлять пользователя долго без краткого обновления. Не выдавать подозрение/ожидание за проверенный факт.

## 15. Что не следует объявлять выполненным

Не выполнены: отключение Windows G2; перенос Repo/Docker; изменение mounts; новые Windows ACL после пользовательского project grant; Godot import/игра; удобный GUI-маршрут из основного профиля; новая VM; установка/исполнение неизвестной локальной модели; новые CI runs; общая приёмка Observatory; полный security review; одинаковый registry-запрос через G2 и Repo; доказательство невозможности всех способов получить Windows metadata; полный review исходного плана; атомарное принятие C-01/C-02/C-03; push этой инициативы.

Сохранённые сводки доступны новому чату через Repo. Raw tool-output и исходное вложение из старого чата не считать автоматически доступными. Сам факт наличия инструмента/файла не является разрешением на его произвольное использование.

**Ближайший смысловой ориентир:** сохранить удобную автономную разработку и ручную проверку результатов, определить реальные границы данных/действий каждого маршрута и подтверждать их конкретными проверками с честными пределами.
