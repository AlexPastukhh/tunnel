# Наш алгоритм создания MCP-плагина

Для изменений **существующего** плагина сначала [INSTRUCTIONS](INSTRUCTIONS.md); для структуры путей — [ARCHITECTURE](ARCHITECTURE.md), для опубликованных Site IDs — [SITES](SITES.md). Этот файл — сценарий **создания**, не второй перечень текущих настроек.

Стандартные команды публикации, формат credential и API аргументы брать из актуальных **Sites / Plugin Creator skills**, а не из скопированной инструкции. Ниже — решения и проверки именно для нашей схемы.

1. **Определить задачу и контур.** Пользователь хочет доступ к Windows, изолированную работу с repo или hosted HTTP API? Не выбирать сайт/проект по факту подключения плагина. Для локального stdio с нужной приватной средой сохранять native Tunnel. Site нужен как отдельный hosted MCP endpoint/диагностика, не обязательная ступень native доступа.
2. **Проверить существующее.** Найти точные Site project/plugin IDs и роли; открыть существующий проект, сохранить аудиторию. В нашем случае два Site уже существуют — см. SITES.md. Не создавать дубликат plugin поверх автоматически созданного Site App.
3. **Подготовить upstream.** Реальный Desktop Commander, точная версия/схемы, доступ и авторизация. Для Repo сначала Docker mounts/network/identity gate; для HOST ясно сообщить широкие права. Проверить read-only вызов. Секретный endpoint/token держать только на сервере.
4. **Собрать контракт proxy.** Worker /mcp, JSON-RPC методы и discovery по действующему skill, корректные tools/list и tools/call, точные upstream аргументы/ошибки. Поддержать нужный JSON/SSE и жизненный цикл session; redirects не следовать без проверки. Не повторять мутации автоматически после timeout.
5. **Настроить presentation и инструкции.** Описание режима, реальные пути, cwd, доступ, недоступные операции и безопасное восстановление. Указать, что подключение не выбирает проект и не просит создать сайт. В Repo Site отдельно описать gate; не рекламировать операции до его выпуска. Legacy embedded UI metadata/resources не переносить автоматически из DC. Native Repo bridge уже убирает их.
6. **Подключить hosting capability.** .openai/hosting.json включает mcp и правильный project_id. UI страницы держать диагностическим и без secret URL. Site auth/audience — самостоятельная граница; public upstream без auth нельзя считать безопасным только потому, что он «туннель».
7. **Проверить локально.** Discovery/initialize, tools/list, схемы, tool results/isError и отказ неподдерживаемых ресурсов. Один безопасный read-only вызов, отказ вне разрешённой зоны; собственный write marker — только в разрешённой папке с последующим удалением. Не использовать пользовательские файлы для случайных write тестов.
8. **Сохранить и опубликовать через Sites workflow.** Получить временный source credential для существующего проекта; применить site-workflow helper по skill. Build/package точного commit, сохранить Site version и deploy с прежней аудиторией. Credential подавать предусмотренным скрытым способом, не коммитить и не печатать. Не обходить workflow случайными ручными auth/config файлами.
9. **Проверить опубликованное.** Дождаться конечного deployment status, проверить именно live /mcp и статус, canonical plugin_id, role/audience. Подключить существующий canonical App, если нужно; не создавать второй вручную. Проверить реальные доступные tools после refresh.
10. **Закрепить результат.** Записать version/source HEAD, состояние каждого контура, проверенные факты и оставшиеся gate. Синхронизировать инструкции по INSTRUCTIONS.md. Репозиторий документации коммитить отдельно от Sites source; push GitHub docs не равен deploy Site.

У Site Worker нет локальной Windows FS/stdio и не следует предполагать доступ к произвольному TCP. Проверять поддерживаемый HTTPS маршрут к upstream. Native Repo и HOST используют сохранённые профили tunnel-client независимо от Worker.

Интерактивная MCP App карточка нужна только при отдельной задаче UI. Тогда следовать текущим extensions/MCP Apps references; наш диагностический Site сам по себе такой карточкой не является.
