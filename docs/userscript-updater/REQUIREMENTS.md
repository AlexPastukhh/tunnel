# Требования к updater и анализу userscripts

Зафиксированы 25.10.2026. Основание — сообщения пользователя в этой беседе. «Требование пользователя», предложение ассистента и непроверенный факт различаются явно. Изменять эти различия при появлении новых подтверждений.

## Принятые пользовательские требования

| ID | Требование | Критерий результата |
|---|---|---|
| U-01 | Обновления работающего userscript только с согласия пользователя | Изменение исходника/сборки в Repo, сохранение файла, commit или PASS анализа сами по себе не меняют файл, исполняемый Loader |
| U-02 | Вне области записи ИИ находится обязательная политика | Правила, доверенный проверяющий/устанавливающий компонент, его настройки и действующая копия недоступны на запись через выданные агенту маршруты; положение «в другой папке Repos» недостаточно |
| U-03 | Источник и назначение выбираются удобно | Есть файловые диалоги для файла-кандидата из Repo и рабочей копии, на которую указывает Loader; при создании назначения нужен понятный выбор нового файла |
| U-04 | Пары регистрируются заранее | Сохраняются имя пары, source/target и выбор последней пары; пользователь может выбрать зарегистрированную пару, добавить, исправить или удалить её без повторного ввода путей каждый раз |
| U-05 | Запуск анализа из того же окна | Для выбранной пары пользователь запускает проверки непосредственно в updater |
| U-06 | Результаты анализа показаны там же | Видны выполняемые проверки, ошибки/находки/пропуски/отсутствие инструмента и итог для конкретной сборки; отсутствие анализатора не отображается как PASS |
| U-07 | «Проверить» и «Обновить» — две отдельные кнопки в одном окне | Проверка ничего не устанавливает и не запускает установку автоматически; после нормального результата пользователь отдельно нажимает «Обновить», видит, что и куда устанавливается, и явно подтверждает замену |
| U-08 | Можно задавать, что скрипту запрещено делать | Поддерживается защищённая политика, выраженная проверяемыми правилами и, где нужно, тестами; обычный текст «запрещено» сам по себе не объявляется enforcement |
| U-09 | ИИ продолжает работать в выделенной Docker-среде | Разработка/сборка/тесты внутри уже разрешённого Repo сохраняются; защищённый Windows runtime не становится новым обходным инструментом агента |
| U-10 | Интерфейс — лёгкая оболочка над инструментами | Переиспользуются готовые анализаторы и их отчёты; не разрабатывается собственный SAST-движок, тяжёлая платформа или обязательный облачный сервис |

Уточнение U-04–U-07/U-10 — последнее и приоритетное. Пользователь отдельно исправил предложение общей кнопки: нужны именно две кнопки, только расположенные в одном удобном месте. Ранее ассистент также предлагал отдельное подтверждение в PowerShell; для повседневной работы выбран единый лёгкий интерфейс. Обычное открытие страницы с уже одобренной версией не должно запрашивать повторную установку.

## Производные критерии безопасности и корректности

Это обоснованные проектные критерии выполнения U-01/U-02/U-07, а не уже реализованные механизмы.

| ID | Критерий |
|---|---|
| C-01 | Действующая копия и доверенные правила находятся вне всех доступных ИИ RW-деревьев; проверяются реальные пути/ACL и альтернативные выданные каналы, а не только строковое имя каталога |
| C-02 | Проверка и подтверждение относятся к зафиксированному набору байтов/SHA-256; устанавливаются эти байты, а не заново прочитанный изменяемый файл из Repo |
| C-03 | Итоговые bundle и зависимости входят в проверяемый состав. Изменение состава/хеша/политики инвалидирует прежний результат |
| C-04 | Нет автоматического допуска по предоставленному ИИ отчёту. Доверенный компонент сам запускает утверждённые анализаторы и проверяет полноту/результат |
| C-05 | Ошибка, таймаут, пропущенный обязательный анализатор или неполная проверка блокируют обычный путь установки; подтверждение не скрывает отрицательный результат |
| C-06 | Недоверенные eslint-конфиги, плагины, npm scripts и иной код из кандидата не исполняются с owner-правами при проверке. Правила/инструменты берутся из доверенной установки |
| C-07 | Нельзя отключить обязательные проверки через комментарии кандидата, его ignore-файлы, произвольные параметры или изменённый конфиг в Repo |
| C-08 | Перед заменой сохраняется прежняя копия вне контроля рабочего агента; есть адресный откат, идентификатор операции и проверка хеша после установки. При отказе/ошибке прежняя версия сохраняется либо ясно сообщается точный восстановимый исход |
| C-09 | Копирование сохраняет байты, включая UTF-8; код не перекодируется через системную ANSI-страницу. Кириллица в названиях/путях пар тоже сохраняется |
| C-10 | Проверяются совпадение source/target, дубли назначений, ссылки/reparse/junction, hardlinks, подмена путей и изменение установленной копии после просмотра |
| C-11 | Первоначальный перевод Loader на защищённый target выполняется явно владельцем Windows. Updater не редактирует базу Tampermonkey скрыто и не меняет @name/@namespace/GM-данные |
| C-12 | Настройки пар, политика и результаты хранятся защищённо; в Git не попадают реальные секреты, bearer, профили подключений, GM originals и приватные журналы. Бэкапы updater — версии кода, а не дампы браузерных данных |
| C-13 | PASS статического анализа означает только отсутствие найденных нарушений соответствующих правил; это не доказательство отсутствия любого нежелательного поведения и не полный security PASS |
| C-14 | Зависание анализатора не блокирует интерфейс без статуса; отмена, повторная проверка и ошибка имеют явный результат. Установка не запускается повторно из-за двойного клика или повторного callback |

## Рекомендации ассистента, ещё не равные установке или отдельному выбору пользователя

- Использовать ESLint с конкретными ограничениями и Semgrep CE с собственными правилами. SonarQube Cloud/GitHub Actions — необязательный дополнительный слой; подключение облака пользователь не поручал выполнять.
- Пример защищённого корня: `%LOCALAPPDATA%\FortisScriptSecurity` с Tool/Policy/Approved/Reviews/Backups. Имена и структура пока предложения; каталог не создан и не проверен на Windows.
- Отдельная среда проверки с закреплёнными версиями анализаторов; исходники и правила передаются как данные/read-only. Доступ ИИ к управлению такой средой должен быть исключён/проверен.
- Для первого интерфейса рассматривались Python/Tkinter или PowerShell/WinForms. Выбор реализации ещё не сделан; GUI/tool-файлы не созданы.
- Полезно показывать version/name/namespace, diff, изменения permissions/endpoints, хеш, итог анализаторов и сведения о резервной копии до подтверждения.

## Что требует проектного решения до установки

1. Конкретный набор обязательных правил и исключений для Notifier и отдельно Helper: этим скриптам законно нужны DOM/Send, некоторые GM-данные и scoped сеть. Нельзя запретить нужную функцию целиком и выдать это за готовую политику.
2. Поведение при ненастроенных анализаторах. По C-05 обычная установка должна блокироваться; отдельный ручной режим не согласован. Не добавлять его молча как обход.
3. Защищённый target: только Approved-каталог инструмента или другой проверенный внешний каталог. Нынешнее назначение внутри Repos нельзя принять как защищённый режим.
4. Кэширование @require конкретной версии Tampermonkey и порядок подхвата новой одобренной копии; проверять на безвредной версии, не обещать мгновенный hot reload.
5. Нужен ли дополнительный SRI pin в установленном Loader. Он потребует смены хеша при каждом обновлении; базовая предложенная удобная схема полагается на защищённый target и контролируемое продвижение проверенных байтов.

## Граница текущей задачи

Пользователь остановил подготовку кода и поручил план/требования/хендофф. Этот этап не разрешает менять live Windows, устанавливать анализаторы на хост, менять mounts/ACL, публиковать GitHub или обновлять браузерные профили. При продолжении агент может готовить исходники и тестировать их в разрешённой среде; owner Windows-настройку пользователь выполняет вручную согласно AGENTS.
