## 1. Что пользователь хочет сейчас

ИИ работает внутри Fortis Repo Docker, но `/workspace/repos` и `/workspace/files` связаны с реальными Windows-папками RW. Если Tampermonkey Loader читает изменяемый JS оттуда, правка ИИ может стать новым кодом в основном браузере. Пользователь хочет отдельный ручной допуск обновлений и правила, которые ИИ не может изменить.

Последние уточнения пользователя:

- Удобно выбирать source из Repo и рабочий target, указанный в Loader, через файловый picker.
- Заранее зарегистрировать несколько пар; потом выбирать пару и нажимать обновление.
- **В одном месте две отдельные кнопки «Проверить» и «Обновить»: первой запускать анализ и смотреть результат, второй после нормальных результатов отдельно подтверждать замену.** Общую кнопку пользователь прямо отверг.
- Это должна быть лёгкая оболочка над готовыми инструментами, не новый собственный анализатор/тяжёлая платформа.
- Обновление требует явного согласия пользователя; доступ ИИ к исходникам не должен автоматически менять исполняемую копию.
- Политика и доверенный механизм находятся за пределами доступных ИИ на запись областей.

Формальные требования: [REQUIREMENTS.md](REQUIREMENTS.md). План: [PLAN.md](PLAN.md). Главное: не возвращать ежедневный UX к отдельному PowerShell-подтверждению или общей кнопке «Проверить и обновить» — это прежние предложения ассистента; последние уточнения выбрали лёгкую оболочку и две отдельные кнопки в одном окне. PowerShell допустим для первоначальной ручной установки/диагностики.

### Исследование хранения профилей

- Notifier хранит профили в **GM Tampermonkey** под `fortis-textbox-profiles-v1`: active profile, имена/ID, promptId, упорядоченные moduleIds, переключатели поведения. Источник: Notifier `src/textbox-module-profiles.js`, подключение GM в `src/runtime.js`.

Текущий synthetic GM/JSON roundtrip с кириллицей прошёл; точная причина порчи при прежнем переносе не установлена. ## 4. Что выяснили о безопасности и что НЕ настроено

- @require исполняет JavaScript с полномочиями установленного Loader. Защищённость самого Loader не делает безопасным произвольный изменяемый target.
- Grants/сетевая политика установленного Loader важны; header внутри подгружаемого JS не выдаёт новые grants. Фактический установленный Loader пользователь считает недоступным ИИ, но его metadata/настройки этим чатом независимо не проверены.
- @connect ограничивает GM_xmlhttpRequest, а не все возможности сетевой передачи браузерного JS. @sandbox DOM сохраняет доступ к DOM; это не запрет нежелательного Send.
- Общий file:// доступ зависит от настроек; загрузка одного @require не доказывает право чтения любого локального файла. Прямой универсальный terminal/Win32 file access стандартные GM API не дают, но локальные сервисы могут расширить последствия доступных команд.
- Предложено разделить Repo-кандидат и одобренную копию вне RW-mounts. Обязательные policy/checker/promoter, настройки/зависимости и approved target тоже должны быть вне контроля агента. Иначе внешний файл политики не создаёт рабочий gate.
- SRI способен остановить изменение ресурса при закреплённом хеше; если агент меняет и хеш/правила, это не защита. Подробности/первоисточники — в PLAN. SRI и защищённое продвижение байтов — разные варианты, не обещать удобный одношаговый update без проверки модели.
- Рекомендованы **ESLint + Semgrep CE**; SonarQube Cloud/GitHub — дополнительная возможность, не подключена. Набор правил/исключений, проверочная среда и GUI toolkit ещё не выбраны окончательно.
- В Notifier нет CI/security config для ESLint/Semgrep/Sonar. Текущий `npm run verify` запускает Node-тесты и build:check. В проверенном Repo PATH есть Python3/Node/npm, нет semgrep/eslint/pwsh/dotnet; ничего нового не установлено.
- После вопроса о picker выполнены только чтения документации/состояния и проверка наличия runtimes. `/workspace/repos/tunnel/runtime/userscript-updater` **не существует**. Ни GUI, ни install script, ни policy file не созданы. Текущий этап добавляет исключительно этот пакет документов и навигацию.

## 6. Как продолжить чистому чату

1. Прочитать AGENTS и этот пакет через Fortis Repo; сверить git status/index.
2. Не возобновлять старый Send-тест и не редактировать main userscript, который текущий Loader может автоматически подхватить.
3. Начать с P-01/P-02: определить модель trusted tool/пар/snapshot/policy и подготовить исходники с backend-тестами внутри Repo. Не начинать с установки Windows или подключения облачного сервиса.
4. Сохранить последний UX: лёгкая оболочка с сохранёнными парами, двумя отдельными кнопками «Проверить» и «Обновить», результатами в том же окне и ручным подтверждением замены. Не делать combined-кнопку или автоустановку после PASS.
5. При развилках из REQUIREMENTS выбрать обоснованный проектный вариант и явно отметить его; недоступность обязательного анализатора не превращать в PASS или молчаливый bypass.
6. После подготовки и проверок предоставить конкретный owner-пакет с исходниками/хешами/первоначальной установкой/откатом. Пользователь выполняет Windows-шаги вручную. Фактическую приёмку записывать после результата, не заранее.
