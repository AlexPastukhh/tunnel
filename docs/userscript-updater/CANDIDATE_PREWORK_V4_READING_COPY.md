## 1. Target, scope и смысл уточнений

**Target установлен:** планируется готовое Windows-приложение с регистрациями, UI, управлением пакетами политик, использованием готовых анализаторов и необязательным контролируемым обновлением внешних файлов/папок. Это не только редактор политик и не только демонстрационный backend.

**Назначение приложения:** пользователь проверяет выбранный материал из доступных Fortis Repo исходников и, если настроен перенос, отдельно одобряет его создание/обновление вне mounts. Перед обновлением текущий исходный состав и хеши должны совпадать с положительно проверенными. Допускаются регистрации без обновления: только анализ и отчёт.

**Реальный путь использования, уточнённый пользователем:** Repo — изменяемая и потенциально опасная зона разработки. Пользователь не запускает результат вручную оттуда; после анализа и одобрения приложение переносит выбранные байты наружу, и пользователь использует внешнюю копию. Для userscripts внешнюю копию читает Loader.

**Явная интерпретация границы:** запрет ручного запуска из Repo относится к потреблению результата пользователем. Он не отменяет ранее разрешённые агентские сборки/тесты внутри выделенной среды. Это не системный запрет всех запусков любых процессов в Docker. Основание — нынешнее «не запускали оттуда вручную» вместе с прежними U-09/I-03. Если пользователь подразумевал также запрет агентских тестов, это отдельное upstream-уточнение, и зависимая часть плана должна быть пересмотрена до исполнения.

**Операции регистрации:** один файл, несколько файлов, папка, папка плюс файлы; при необходимости несколько явных source → target mappings. Это прямое уточнение пользователя, расширяющее прежнюю альтернативу file/folder. Новая функциональность не считается уже реализованной.

Версия v4 уточняет план по последнему ответу пользователя и публикует новый reading snapshot. Свежие source-состояния и выполненный по отдельному поручению cleanup RED-01 переиспользованы из v3 без повторных runtime probes и без новых изменений кода. Реализация checker, установка инструментов, Windows-команды/GUI, ACL/mounts, изменения Loader, запуск проверяемого проекта, обновление canonical STATE/JOURNAL и создание PRS не выполняются.

## 4. DRLD: один пользовательский путь с самостоятельными сценариями

Все четыре DS имеют общую версию **v2, candidate** как целые подробные маршруты. Источник — принятые прежние ограничения и текущие ответы. Benefit/Concept/подробный путь — части одного Scenario, а не три самостоятельных lifecycle. Детали, добавленные ассистентом для осуществимости, остаются предложениями до принятия композиции.

### DS-01/v2 — регистрация проверяемого проекта

**Fundamental Benefit:** пользователь сохраняет предмет проверки и переносов один раз и затем повторяет нужную операцию без набора путей заново. Польза наблюдается при повторном выборе сохранённого проекта.

**Scenario Concept:** выбрать source, пакеты и необязательные mappings в доверенном UI; сохранить регистрацию.

**Detailed Desired Real-Life Scenario:**

1. Пользователь открывает установленное приложение. Prerequisites — подготовленная trusted установка; input — доступный проект из примонтированного дерева.
2. Он задаёт имя и выбирает один или несколько source-элементов: файл/папку/смешанный набор. Приложение показывает развёрнутый состав и разрешённые пути. Физические aliases не считаются независимыми объектами.
3. Пользователь подключает совместимые пакеты. Видны их правила/параметры, область применения и итоговые конфликты.
4. Для check-only target не требуется. Для переноса пользователь задаёт mappings на отдельные внешние файлы/папки. Нельзя получить скрытое последнее «победившее» правило при наложении папки и отдельного файла на один target.
5. Отмена picker не сохраняет полузапись. При ошибке чтения настроек реестр не сбрасывается. После сохранения и перезапуска выбор восстанавливается; это точка пользы.
6. Изменение source-путей, привязок, состава переноса или target инвалидирует применимость прежнего положительного результата.

Основание: N-02/N-04; U-03/U-04; ответы F-U-01/04; PR-01/02/12.

### DS-02/v2 — прямое управление общими пакетами

**Fundamental Benefit:** одна правка правил меняет проверки всех проектов, которые используют этот пакет; исключения можно сохранить отдельной копией пакета без обязательного управления версиями.

**Scenario Concept:** редактировать действующий пакет; привязанные проекты используют новое содержимое; отдельный пакет сохраняет другой набор правил.

**Detailed Desired Real-Life Scenario:**

1. Пользователь открывает раздел пакетов, создаёт/копирует пакет либо редактирует существующий. Inputs — поддерживаемые настройки ESLint/Semgrep и значения параметров. Source-конфиги из Repo не подхватываются.
2. Пользователь меняет правила/параметры в форме; расширенная конфигурация допустима для поддерживаемых доверенных инструментов. Свободное описание желаемого поведения само по себе не становится проверкой.
3. Приложение валидирует конфигурацию и сохраняет пакет безопасно. Некорректное сохранение не разрушает прежний рабочий пакет.
4. После успешного изменения пакет действительно применяется ко всем привязанным проектам. Не требуется отдельное применение новой ревизии к каждому. Существующие проверки этих проектов становятся устаревшими; активные jobs не получают новые правила посреди своего прохода.
5. Чтобы сохранить два набора, пользователь создаёт независимую копию и меняет привязки выбранных проектов. Например, сначала копирует P в P2, переводит часть проектов на P2 и редактирует P2; остальные остаются на P. Возможна и обратная схема: сохранить старое в P-old, затем редактировать P.
6. При удалении используемого пакета привязки нужно явно заменить/убрать; отсутствующий пакет не превращается в проверку без правил. Список затронутых проектов можно показывать как информацию, без отдельного version/pinning workflow.

Внутренний хеш effective policy в отчёте — техническое доказательство применимости, **не пользовательская система версий пакетов**. Основание: N-03; ответ F-U-03; PR-04B.

### DS-03/v2 — проверка, понятный отчёт и применимость результата

**Fundamental Benefit:** пользователь получает конкретные находки и видит границы проверки именно выбранного состава; для check-only этим достигается самостоятельная польза.

**Scenario Concept:** выбрать регистрацию → «Проверить» → получить отчёт по снимку без установки или запуска кандидата под owner.

**Detailed Desired Real-Life Scenario:**

1. Пользователь нажимает «Проверить». Приложение фиксирует настройки регистрации и пакетов, разворачивает inventory всех выбранных source и строит отдельный защищённый снимок.
2. Каждому выбранному файлу назначается понятная обработка: проверяется подходящим анализатором; явно исключён; ресурс учтён по хешу; код не поддерживается; ошибка чтения/разбора. Хеширование ресурса не называется его анализом.
3. Установленные ESLint/Semgrep читают снимок с доверенными явно заданными правилами. Программа сопоставляет собственный inventory с реальными входами и структурированными результатами инструментов. Проектные npm scripts/config/plugins/тесты автоматически под owner не выполняются.
4. В UI видны ход, отмена, ошибки инструментов и coverage. Отсутствие findings не является PASS, если нужные файлы не были обработаны или обязательные правила пропущены.
5. Итог показывает файлы, анализаторы/версии, правила, findings с расположением, ошибки/пропуски и идентичность состава. Это точка пользы. «Положительно проверено» означает выполненные условия соответствующей политики, а не доказанную безопасность любого поведения.
6. Если source, пакет, registration или инструмент меняются, старый отчёт остаётся историей, но его допуск к новому материалу неприменим. Скрытый rerun из кнопки «Обновить» не заменяет отдельное «Проверить».

Основание: N-01/02/04; FR-06/07; ответ F-R-02; PR-05. Основные заявления JSON engines подтверждены документацией, но Windows-контракт и реальные negative outcomes ещё не проверены.

### DS-04/v2 — перенос наружу, использование и восстановление

**Fundamental Benefit:** пользователь использует отдельный внешний результат, который соответствует положительно проверенному набору, и может восстановить прежний при неудаче.

**Scenario Concept:** положительная применимая проверка → отдельное подтверждение → повторная сверка source и политики → перенос проверенных байтов → read-back → использование внешней копии.

**Detailed Desired Real-Life Scenario:**

1. Пользователь выбирает «Обновить» для регистрации с mappings. Приложение строит и показывает конкретный план относительно **фактического внешнего target**: файлы, которые будут созданы, изменены или удалены, сохраняемые лишние/исключённые элементы, source/target, применимый отчёт и backup. Для текста доступны содержательные diff; для бинарных изменений — явно обозначенные old/new hashes и размеры. Неизменённые элементы могут быть свернуты. Один Git diff source не заменяет это сравнение.
2. Подтверждение относится к показанному плану, его checked snapshot/policy и исходному состоянию target. Если план или target изменились после просмотра, прежнее подтверждение не используется: требуется новый просмотр. **Непосредственно перед применением** приложение заново проверяет текущие хеши **и состав** source относительно положительного отчёта: изменение файла, добавление/удаление в выбранной папке, новые пути либо изменение разрешения ссылок не пропускаются из-за совпавшего хеша одного JS. Проверяются также effective policy, registration/tool fingerprints и ожидаемое состояние target.
3. Несовпадение останавливает обновление и требует отдельной новой проверки. Скрытой переоценки кандидата с последующей автоустановкой нет.
4. При подтверждении программа использует защищённый проверенный снимок. Повторная сверка текущего source и использование снимка нужны **вместе**: одна сверка не защищает от чтения новых байтов между проверкой и копированием, а один снимок без сверки не выполняет явно заданное пользователем условие актуальности.
5. Программа готовит новые обычные файлы в staging, сохраняет прежнее состояние и применяет заявленный набор mappings с журналом. Она не создаёт Junction/hardlink или автоматическую синхронизацию из source вместо независимых копий. Если файл отсутствует, создание выполняется здесь после допуска.
6. При изменении source после финальной сверки непроверенные новые байты не подмешиваются: источник переноса — снимок. Допуск к следующему обновлению потребует новой проверки. Согласованный состав важнее совпадения размера/времени изменения файла. Подмена source во время создания/сверки снимка должна давать отказ либо стабильный доказанный snapshot, не смесь.
7. Если возникает ошибка/занятость/частичный сбой, UI сообщает точное состояние и доступное восстановление. Для набора на нескольких томах не обещается недоказанная единая атомарная операция. Общий «успех» возможен только после проверки всех mappings; частичный результат не маскируется под полный.
8. После read-back приложение показывает установленный состав. Пользователь запускает/открывает внешнюю копию согласованным способом; Loader читает внешний JS. Кнопка обновления сама не запускает произвольную команду из Repo. Для Tampermonkey отдельно проверяются фактическая версия и cache.
9. Откат — отдельное подтверждаемое действие с проверкой backup, текущего target и восстановленных байтов. Файлы/данные вне управляемого состава не удаляются.

Основание: FR-01/03/05/06; ответы F-U-02/04/F-R-03; PR-05/06/07/12. Пользовательский data/layout contract и поведение занятого приложения конкретизируются до первого обновления соответствующего проекта.

### F-R-01: что закрывается ответом, а что ещё проверять

Правильное решение выбрано: приложение и политики снаружи, source-change не должен менять installed runtime. Под «обрубить связи» понимается отсутствие исполняемых импортов, auto-sync, linked approved files и подхвата Repo configs/deps. Намеренное **чтение исходников проекта** остаётся: иначе checker не сможет работать.

Пример будущей проверки: изменить в Repo безопасный config-canary; установленный checker не должен его исполнять. Затем из охваченного agent route попытаться изменить специальный тестовый trusted marker и проверить отказ. Успех одного такого теста не доказывает закрытость всех неизвестных каналов. Значения секретов не читаются; Windows выполняет пользователь вручную.

### F-R-02: инструменты помогают, но итоговую полноту устанавливает оболочка

Да, JSON-отчёты дают файлы/пути, находки, расположение, правила и ошибки. Пример корректного отчёта: «в составе 40 файлов; 25 проверены ESLint/Semgrep; 10 ресурсов учтены по хешу; 3 явно исключены; 2 кодовых файла не поддерживаются». Эти числа — **пример формата**, не результат реального scan.

Недостаточно посчитать только полученные `results`: инструмент может не вернуть ни одной находки или вообще не обработать нужный файл. Поэтому app сравнивает собственный manifest ожидаемых входов с фактической обработкой, errors/skips/limits и policy applicability. Ни «нет findings», ни «exit 0», ни «есть hash каждого файла» по отдельности не дают общего PASS. Что именно блокирует обновление, видно в применённой политике; отсутствие обязательной проверки не обходится молча.

### F-R-03: прямой ответ покрывает часть механизма

Сценарий stale source: проверен A, затем source стал B. Требование повторной сверки блокирует обновление — эта нужная защита теперь явно установлена. Сценарий race: после сверки файл изменился; копирование из protected snapshot не подмешивает B. Сценарий partial copy: из десяти mappings обновлены три, четвёртый занят — hashes исходника сами по себе не восстанавливают прежние target. Нужны staging, backup, journal, известные состояния и rollback. Поэтому весь Risk ещё нельзя назвать resolved.

Нового подтверждённого Problem (`F-P`) о ещё не созданном приложении не заявляется. Отсутствие будущих тестов — Evidence Gap исполнения, не дефект результата планирования.

$ErrorActionPreference = 'Stop'

Исчезнувший source-файл, которым ранее управляло приложение, предлагается удалить из соответствующей внешней копии и показывается как удаление. Подтверждение пользователя относится к этому точному плану. Другие target-only файлы и data вне managed scope нельзя молча включать в очистку; первый импорт существующей папки требует явного scope.

Это конкретная техническая рекомендация, а не приписанное пользователю решение «автоматически удалять вообще всё лишнее». До подтверждения план ничего не меняет. Изменение source/target/политики после просмотра отменяет его применимость. Пользователь отменяет неподходящий план и меняет source/регистрацию/состав перед новой проверкой; обязательные дополнительные галочки для каждой операции не вводятся без отдельного основания.

PR-13D REQUIRES PR-03/05/06/07/12 и preview/confirmation WR-26/27. Он SUPERSEDES PR-13C в рекомендации композиции, а не переписывает исторический v3. PR-13A (всегда managed-sync), PR-13B (add/replace only), PR-13C (режим для каждой регистрации) остаются историческими альтернативами; никакая из них не объявляется user-committed. **A4 = основной A2 + PR-13D**, с полным хендоффом, остаётся candidate до принятия всей композиции.

**Почему Git не заменяет backup updater.** По [официальной книге Git](https://git-scm.com/book/en/v2/Git-Basics-Undoing-Things) закоммиченные данные обычно восстановимы, а никогда не сохранённые в commit изменения могут быть потеряны. Git источника также не гарантирует сохранность прежней внешней installed-копии, локальных внешних настроек и состояния частичного переноса. Поэтому Git помогает восстановить исходный код, а backup/journal updater отдельно восстанавливает фактическое состояние target перед операцией. Автоматический commit всех Repo-файлов, untracked данных или `.git` в external copy не добавляется.

Новый обязательный пользовательский вопрос по этому общему поведению не требуется. При конкретной регистрации ещё уточняются scope, данные и операции, которые реально попадут в preview.

### 14.9. Точная граница полномочий и первой следующей работы

Можно без новой установки: прочитать относящиеся источники, проверить status/paths, сопоставить выбранные правила/coverage, уточнить proposal defaults и подготовить reviewable пакет. Нельзя на основании одного хендоффа: устанавливать/запускать trusted app на Windows, менять ACL/mounts, удалять Junction, переустанавливать Loader, читать GM/private profiles, выполнять native Send или подменять текущее развитие Repo другим проектом.

Для разработки после принятия состава: сначала выбрать/создать отдельный source-каталог checker в разрешённом Repo; зафиксировать форматы регистраций/пакетов/manifests и проверить маленький вертикальный путь. Не писать всё сначала как монолитный UI, не делать свой анализатор, не заменять CLI-вызовы неподписанным отчётом агента. Пакеты/приложение разрабатываются в source, но **действующие** пакеты/исполняемые файлы после установки не подхватываются оттуда.

Достаточное первое evidence — маленький набор valid/invalid fixtures и реальный host запуск установленных CLI по заранее подготовленному ручному пакету. Код проекта не исполняется под owner ради статического scan. Устанавливаемые bytes соответствуют snapshot; current-source hash/inventory перед update обязательны дополнительно, а не заменяются snapshot.

В Git проекта коммитить только собственные относящиеся файлы после повторной проверки staged bytes. Не коммитить диагностический RED-01, чужие 26 Helper entries или raw secrets попутно. Не делать push/project deployment без отдельного поручения. Публикация этого requested reading copy в `forfiles` — отдельное явно разрешённое действие, не общий push-допуск.
