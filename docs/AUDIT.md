# Аудит вызовов и запрет операций (текущее состояние и целевая спецификация)

**Важно:** ниже отдельно обозначены наблюдаемые факты и **требования к будущей реализации**. Наличие этого документа **не включает** журнал или принудительные запреты. Модель путей — [ARCHITECTURE](ARCHITECTURE.md), действующие границы доступа — [ACCESS](ACCESS.md).

## Что имеется сейчас

- Desktop Commander предоставляет `get_recent_tool_calls`: локальную историю `tool-history.jsonl`, ограниченную и сокращаемую; по описанию инструмента — до 1000 последних вызовов в памяти, большие ответы опускаются. Это не полноценный неизменяемый аудит всех событий.
- В ответах `get_config` при проверке 12.10.2026: HOST `telemetryEnabled=true`, native Repo `telemetryEnabled=false`. Телеметрия **не означает** журнал всех MCP-запросов с надёжной привязкой к чату.
- [Observatory P1](OBSERVABILITY.md) — внешний read-only монитор health/metrics и обезличенных ошибок; он не находится на обязательном пути операций и не предотвращает вызовы.
- В датированной копии Repo Bridge вызовы пересылаются upstream; обязательная allow/deny политика и персистентный audit writer в ней **не обнаружены**.
- Repo Site на проверке 12.10.2026 не имеет активного upstream для file/terminal. Это не отключает native Repo.

**Не подтверждены:** полнота исторического журнала всех чатов, достоверный chat/session ID, одинаковое логирование native и Site, сохранность всех прошлых payload и существование обязательного Policy Gate.

## Новый read-only просмотр истории (source MVP, 2026-10-16)

Добавлен переносимый [audit CLI](../observatory/activity_audit.py),
читающий локальный файл tool-history.jsonl Desktop Commander из отдельного
контекста Repo или G2. По умолчанию отдаются только метаданные: время,
tool, категория, длительность, наличие terminal command/input и явно
отмеченная ошибка. Outcome unverified не означает успешного исполнения.
Observatory source поддерживает opt-in /api/activity и две дорожки G2/Repo;
путь G2 должен быть доступен только по обычным правам текущего пользователя,
обхода Windows ACL нет.

Точный текст команды разрешён только в доверенном интерактивном локальном
терминале через --unsafe-show-commands-local; HTTP/API его не раскрывает.
Raw command/input может содержать токены — не отправлять в чат, Git, screenshots.
Уже существующий DC log не является достоверной историей всех чатов:
rolling ~1000 calls, усечённые большие ответы, нет trusted chat ID,
отсутствуют другие MCP routes и внутренние дочерние команды процессов.
Никакого обязательного gateway, OS tracing или policy enforcement это не включает.
Live Windows P1, G2 и Repo Bridge не менялись; приёмку после деплоя не заявляем.

## Цель отдельной разработки

Для **каждого** вызова через контролируемые HOST/Repo native и активные Site-маршруты: до исполнения получить решение `ALLOW/DENY`, зафиксировать попытку, после исполнения — фактический исход; запрет должен исключать передачу команды исполнителю. Если проверяющий компонент недоступен — **fail closed** для защищённых операций.

Это не охватывает операции ChatGPT через другие плагины, локальные действия людей или обход вне заданных MCP-маршрутов; требовать «все действия чатов вообще» без такого ограничения нельзя.

## Минимальная модель события (проект)

| Поле | Семантика |
|---|---|
| `event_id`, `timestamp_utc` | Уникальность и время попытки/результата |
| `route`, `component_id` | native HOST / native Repo / конкретный Site |
| `mcp_method`, `tool_name`, `operation` | Вызванный метод и класс действия |
| `resource_ref` | Минимальная нормализованная и санитизированная цель, без содержимого файлов |
| `decision`, `policy_rule_id` | `ALLOW/DENY/ERROR`, правило и версия политики |
| `execution_status`, `duration_ms` | Успех, отказ, ошибка или неопределённый результат |
| `request_id`, `session_ref` | Корреляция **только при достоверном источнике**; отсутствие обозначать `unknown` |

Предпочтительны парные события `attempt` и `result`, связанные `event_id` / correlation ID. При прерывании после разрешения оставить отметку `outcome_unknown`, не записывать фиктивный успех.

**Не сохранять по умолчанию:** полный текст команд, MCP arguments/responses, содержимое файлов, промпты/переписку, значения env, пароли, токены, runtime-key. Даже имена файлов и аргументы могут быть чувствительными: нормализовать и маскировать. Для специальных forensic-процедур понадобится отдельное согласование.

## Принудительная политика (проект)

1. Инвентаризировать **все** зарегистрированные native/Site пути и их точные `tools/list` / `tools/call`, чтобы нельзя было обойти проверку альтернативным маршрутом.
2. Разделять профили HOST и Repo. Для HOST рассмотреть default-deny с минимальным набором разрешённых операций. Для Repo — отдельный scope по проектам и допустимым операциям.
3. Проверять вызываемый инструмент, тип операции и целевой ресурс **перед передачей исполнителю**. Правила должны храниться вне областей записи самого чата; запретить изменение policy тем же рабочим инструментом.
4. Подкрепить MCP gate реальными Windows ACL/учётной записью и Docker mounts, правами, network policy. Произвольные PowerShell/Python/Bash-процессы могут обойти фильтр операций отдельных файловых инструментов.
5. Закрывать защищённый маршрут при отказе policy/audit компонента; логировать сам отказ без приватного payload. Уведомления и GUI — вспомогательная функция, **не** enforcement.
6. Для Site проверять отдельно Site upstream/auth и native-маршрут: Site-only gate не ограничивает независимый native Tunnel.

## Журнал и срок хранения (не выбраны)

Целевая защита: запись за пределами writable Docker mounts и доступных HOST-путей, минимальные права append/чтения, ротация, квоты, контроль целостности и устойчивость к сбою диска. Срок хранения, доступ владельца, экспорт, уведомления и допустимые метаданные согласовать до запуска. Секреты и приватные upstream URL никогда не отправлять в Git/diagnostic ZIP.

## Достаточная проверка после реализации

- Положительная: разрешённое чтение/тест в заранее выбранном тестовом каталоге, событие `ALLOW` и проверенный результат.
- Отрицательная: попытка записать/удалить **только синтетический marker** вне разрешённого scope; `DENY` и доказанное отсутствие эффекта.
- Обходы: попытка эквивалентного действия через shell и альтернативный native/Site маршрут; запрет на уровне ОС/контейнера должен сохраняться.
- Отказ компонентов: недоступность проверки/журнала приводит к блокировке, а не silent allow.
- Журнал: сопоставление количества реальных проб с попытками/исходами, обратное чтение, проверка маскирования и срока хранения.
- После timeout: проверить результат до повтора. Никаких тестов на реальных пользовательских файлах, секретах или масштабном экспорте.

**Статус на 12.10.2026:** документированная проектная спецификация. Ни развернутого обязательного gate, ни полного аудита, ни этих end-to-end проверок настоящая документационная задача не выполняла.
